引言：从语言模型到智能体

大语言模型（LLM）本质上是一个"文本生成器"——给定输入，生成续写。 但人类的智能远不止于语言：我们能感知环境、制定计划、使用工具、执行动作、从反馈中学习。 Agent（智能体）正是让 LLM 突破"纯文本对话"的局限，使其能够自主地与外部世界交互、完成复杂任务的范式。

Agent 的核心定义：Agent = LLM（大脑）+ 工具（手脚）+ 记忆（经验）+ 规划（策略）。 它不仅能"说"，还能"做"——搜索网页、执行代码、调用 API、读写文件、操控浏览器， 并根据执行结果动态调整后续行动。
图 1：LLM Agent 核心架构。以 LLM 为中心大脑，连接工具、记忆、规划和环境四大模块，形成感知-思考-行动的闭环。

与传统的 LLM 对话相比，Agent 范式带来了质的飞跃：

Agent 能做到的

  • 自主搜索信息并整合多源知识
  • 编写并执行代码解决计算问题
  • 调用外部 API 完成真实操作
  • 多步骤推理与自我纠错
  • 持久记忆跨会话的上下文

传统对话 LLM 的局限

  • 知识冻结在训练截止日
  • 无法执行实际操作
  • 无法验证自己的回答
  • 上下文窗口有限
  • 易产生幻觉且无法自查

一、Agent 核心执行原理

1.1 Agent 执行循环：感知-思考-行动-观察

所有 Agent 的核心都是一个迭代执行循环：接收输入（用户请求或环境反馈）， LLM 进行推理和决策，选择一个动作（调用工具或直接回答）， 观察执行结果，再决定下一步。这个循环持续到任务完成。

图 2：Agent 执行循环。LLM 在每一轮中进行思考、决定行动、观察结果，不断迭代直到任务完成或判断无需继续使用工具。

1.2 核心推理范式：ReAct

ReAct（Reasoning + Acting）（Yao et al., 2022）是 Agent 最基础且最广泛采用的推理范式。 它要求 LLM 在每一步先生成推理过程（Thought），再决定动作（Action）， 交替进行推理与行动，使模型的决策过程透明可追踪。

ReAct 格式示例（单步）：

Thought：用户问"今天北京天气如何"，我需要调用天气查询工具获取实时信息。
Action：get_weather(city="北京")
Observation：{"temperature": 28, "weather": "晴", "humidity": 45%}
Thought：我已获得天气信息，可以直接回答用户。
Answer：今天北京天气晴朗，气温 28°C，湿度 45%，非常适合户外活动。

1.3 进阶推理范式

推理范式 核心思路 适用场景 代表工作
ReAct 交替进行 Thought → Action → Observation 通用 Agent 任务 Yao et al., 2022
Plan-and-Execute 先生成完整计划，再逐步执行，失败时重新规划 复杂多步骤任务 Wang et al., 2023
Reflexion 执行后进行自我反思，将反思写入记忆指导后续 需要试错学习的任务 Shinn et al., 2023

图 3：ReAct 与 Plan-and-Execute 对比。ReAct 逐步交替推理和行动，灵活但调用次数多；Plan-and-Execute 先一次性规划，执行效率更高。

二、工具调用（Function Calling）原理

2.1 Function Calling 的核心机制

Function Calling（工具调用 / 函数调用）是 Agent 与外部世界交互的核心能力。 模型接收用户请求和可用工具的描述（JSON Schema）， 判断是否需要调用工具，并生成结构化的调用参数（而非自然语言）， 由运行时执行后将结果返回模型。

图 4：Function Calling 完整执行流程。LLM 生成结构化调用意图，宿主程序执行并返回结果，LLM 据此生成最终回答。

2.2 工具描述的设计（Tool Schema）

工具描述的质量直接影响 Agent 调用工具的准确性。一个好的工具描述需要包含清晰的名称、功能说明、参数定义、返回值说明。

工具描述示例（JSON Schema 格式）： 
{
  "name": "search_web",
  "description": "搜索互联网获取实时信息。当用户询问近期事件、实时数据或你不确定的事实时使用。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "搜索查询关键词，应简洁且具体"
      },
      "num_results": {
        "type": "integer",
        "description": "返回结果数量，默认5",
        "default": 5
      }
    },
    "required": ["query"]
  }
}

2.3 主流工具类型

工具类型 功能 示例 安全风险
信息检索 搜索和获取外部信息 Web Search、RAG 检索、Wikipedia 低
代码执行 编写并运行代码 Python REPL、Shell、Jupyter 高（需沙箱）
API 调用 调用外部服务 天气 API、邮件发送、数据库查询 中（需权限控制）
文件操作 读写文件系统 文件读取、写入、目录遍历 中（需路径限制）
浏览器控制 模拟人类浏览网页 Playwright、Puppeteer、Selenium 中
多模态工具 处理图像/音频/视频 图像生成、OCR、语音合成 低
MCP 服务器 标准化工具协议（Model Context Protocol） 任意外部服务通过 MCP 接入 取决于服务

2.4 并行工具调用与工具链

现代 Agent 支持在单次推理中并行调用多个工具（parallel tool calls）， 大幅降低多工具场景的延迟。同时，复杂任务往往需要工具链（Tool Chaining）—— 一个工具的输出作为另一个工具的输入。

1

并行调用

同时查询北京和上海天气：LLM 一次生成两个 tool_call，运行时并行执行，大幅减少等待时间。

2

工具链

搜索论文 → 下载 PDF → 提取内容 → 总结要点：每步结果驱动下一步调用，形成有向无环图（DAG）。

3

条件分支

根据工具返回结果决定后续路径：如果搜索无结果则换关键词，如果代码报错则修复重试。

4

错误恢复

工具调用失败时，Agent 可解析错误信息，调整参数重试或切换备选工具，无需人工干预。

2.5 工具调用的内部实现原理

Function Calling 看似简单——模型输出 JSON、运行时执行、结果返回——但其内部实现涉及 Prompt 工程、结构化输出控制、多轮状态管理、Token 格式设计等多个技术层面。 理解这些细节对于构建可靠的 Agent 系统至关重要。

（1）System Prompt 中的工具注入

当开发者通过 API 传入 tools 参数时，LLM 提供方会将工具描述注入到 System Prompt 中， 成为模型上下文的一部分。不同厂商的注入格式不同，但核心模式一致：

工具注入的 System Prompt 典型格式： 
# Available Tools

You have access to the following tools. To call a tool,
respond with a JSON object in the following format:

<tool_call>
{"name": "tool_name", "arguments": {"param1": "value1"}}
</tool_call>

## Tools

### get_weather
Description: 获取指定城市的天气信息
Parameters:
- city (string, required): 城市名称
- unit (string, optional): 温度单位, "celsius" or "fahrenheit"
Returns: 包含温度、天气状况、湿度的 JSON 对象

### search_web
Description: 搜索互联网获取实时信息
Parameters:
- query (string, required): 搜索关键词
- num_results (integer, optional): 返回数量, 默认 5

这种注入机制意味着：工具调用本质上是一种受控的文本生成任务——模型并不"原生理解"JSON Schema， 而是通过 SFT/RLHF 训练学会了"看到工具描述后，在需要时生成符合格式的调用指令"。

（2）模型如何生成结构化工具调用

LLM 生成工具调用时，需要在自然语言和结构化 JSON 之间切换。 不同模型采用不同的实现策略：

图 5：工具调用的三种结构化输出策略与模型内部 Token 生成过程。特殊 Token 标记是当前主流方案，约束解码保证格式正确性，后处理解析最为灵活。

（3）Stop Reason 与流式工具调用

在流式输出（streaming）场景下，运行时需要实时判断模型是否正在生成工具调用。 主流 API 通过 finish_reason / stop_reason 字段区分：

Stop Reason 含义 运行时处理
stop / end_turn 模型完成回答，无工具调用 直接将文本返回用户
tool_calls / tool_use 模型请求调用工具 解析调用 → 执行 → 结果回填 → 继续推理
length 达到 max_tokens 截断 工具调用可能不完整，需要错误处理
流式工具调用的挑战：在 streaming 模式下，运行时需要逐 token 累积输出并在检测到完整的 tool_call JSON 后立即触发执行。如果模型生成了不完整的 JSON（如被 max_tokens 截断）， 需要进行回退重试（增大 max_tokens）或降级为纯文本回答。 部分框架通过缓冲整个 tool_call block 后再解析来避免不完整 JSON 的问题。

2.6 多轮工具调用的状态管理

Agent 完成一个复杂任务往往需要多轮工具调用。每一轮的消息都必须按照严格的角色交替模式 组织到上下文中，形成完整的对话历史：

图 6：多轮工具调用的上下文消息结构。每轮调用都追加 assistant(tool_call) → tool(result) → assistant(response) 三条消息，通过 tool_call_id 关联。

2.7 工具调用的错误处理与鲁棒性

生产级 Agent 系统必须处理各种工具调用的异常情况。良好的错误处理机制是 Agent 可靠运行的基础：

1

JSON 解析失败

模型生成的 JSON 格式不合法（如缺少引号、多余逗号）。处理方式：使用宽松 JSON 解析器（如 json5）自动修复； 或将错误信息回传模型让其重新生成。约束解码可彻底消除此问题。

2

工具不存在

模型"幻觉"出不存在的工具名。处理方式：在解析阶段验证工具名是否在已注册列表中； 将错误信息返回模型。训练数据质量和 System Prompt 设计可降低此类错误的概率。

3

参数类型错误

如将字符串传入 integer 类型参数。处理方式：基于 JSON Schema 校验参数类型， 可尝试自动类型转换（"5"→5），或返回模型重新生成。

4

工具执行超时 / 异常

外部 API 无响应或返回服务端错误。处理方式：设置超时时间，将错误信息（如 "API timeout after 30s"） 作为 tool 消息返回模型，让 Agent 自行决定重试或换方案。

重试机制的设计：成熟的 Agent 框架通常实现分层重试—— (1) 自动重试：对网络超时等瞬态错误自动重试 2-3 次，带指数退避； (2) 模型重试：将持续错误信息返回 LLM，让模型调整参数或策略后重新调用； (3) 降级处理：多次失败后，模型基于已有信息给出最佳回答，并告知用户部分工具不可用。 设定全局最大工具调用次数（如 25 次）防止无限循环。

三、Agent 训练与微调

3.1 让 LLM 学会使用工具：训练概述

预训练的 LLM 并不天然具备工具调用能力。需要通过专门的训练和微调， 让模型学会：(1) 何时应该调用工具而非直接回答；(2) 选择正确的工具；(3) 生成格式正确的调用参数； (4) 整合工具返回的结果生成最终回答。

图 7：Agent 能力的训练流水线。从预训练的结构化理解到 Tool Use SFT，再到 Agent RL 和安全对齐，逐步构建完整的 Agent 能力。

3.2 Tool Use SFT：工具调用微调

Tool Use SFT 是赋予 LLM 工具调用能力的核心步骤。训练数据为结构化的工具调用轨迹， 模型需要学习在什么情况下调用什么工具、如何生成正确的参数。

Tool Use SFT 训练样本格式： 
System: 你是一个有帮助的助手，可以使用以下工具：
  - search_web(query: str) → str：搜索网络
  - calculator(expression: str) → float：计算数学表达式

Assistant: [调用工具] search_web(query="2024年诺贝尔物理学奖")
Observation: {"results": [{"title":"2024年诺贝尔物理学奖揭晓", "snippet":"John Hopfield 和 Geoffrey Hinton 因在人工神经网络的机器学习基础性发现和发明而获奖"}]}
Assistant: 2024年诺贝尔物理学奖授予了 John Hopfield 和 Geoffrey Hinton，获奖理由是他们在利用人工神经网络进行机器学习方面做出了基础性的发现和发明。

3.3 Agent 训练数据的设计与准备

高质量的 Agent 训练数据是模型获得工具调用和任务执行能力的关键。 数据的设计需要覆盖多种工具、多种调用模式、多种错误场景。

3.4 Agent 强化学习（Agent RL）

SFT 只能学习"示范"中的固定模式。Agent RL 则让模型在真实或模拟环境中自主探索， 通过任务完成与否作为奖励信号，优化整个决策序列。

1

环境交互式训练

模型在沙箱环境（如 WebArena、SWE-bench）中执行任务，每个完整轨迹的成功率作为奖励。不再依赖人工标注"正确答案"。

2

奖励设计

任务成功 = +1，失败 = 0，过程奖励（中间步骤正确 = +0.1）。GRPO/PPO 用于优化策略。DeepSeek-R1 的 RLVR 思路同样适用于 Agent。

3

拒绝采样（Rejection Sampling）

让模型多次尝试同一任务，从成功的轨迹中筛选最优的作为 SFT 数据。介于 SFT 和 RL 之间的高效策略。

4

自我反思训练

Reflexion 范式：执行失败后让模型生成反思总结，写入记忆后重试。反思本身也作为训练数据。

四、Agent 记忆系统

4.1 记忆的分类与作用

人类完成复杂任务依赖记忆——Agent 同样需要记忆来维持上下文、积累经验和存储知识。 Agent 的记忆分为短期记忆、长期记忆和工作记忆三类。

图 9：Agent 记忆系统架构。短期记忆存储当前对话，工作记忆追踪任务状态，长期记忆通过向量数据库持久化跨会话知识。

4.2 RAG 与长期记忆

RAG（Retrieval-Augmented Generation）是 Agent 长期记忆的核心实现方式。 将历史经验、文档知识等编码为向量存储在数据库中， 在需要时通过语义相似度检索，注入到 Agent 的上下文中。

5.3 MCP（Model Context Protocol）简介

MCP 是 Anthropic 提出的开放标准协议，旨在为 LLM Agent 提供统一的工具接入方式， 已成为 Agent 工具生态的重要基础设施。由于其重要性和复杂性，下一节将单独详细介绍 MCP 协议的完整原理。

六、MCP（Model Context Protocol）协议详解

MCP（Model Context Protocol）是 Anthropic 于 2024 年底发布的开放标准协议， 旨在为 LLM 应用提供统一的外部数据和工具接入方式。MCP 的核心理念类似于 "AI 时代的 USB-C"—— 定义一套标准接口，让任何 AI 应用（Host）都能与任何外部服务（Server）即插即用地连接， 彻底消除传统 Agent 开发中"每个工具都要写一套适配代码"的碎片化问题。

6.1 MCP 解决的核心问题

在 MCP 出现之前，Agent 的工具集成面临 N×M 问题：

传统方式：N×M 适配

  • 每个 Agent（Claude/GPT/Gemini...）需要分别适配每个工具（GitHub/Slack/DB...）
  • N 个 Agent × M 个工具 = N×M 个集成代码
  • 工具描述格式各异，不可复用
  • 新增一个 Agent 需要重新适配所有工具

MCP 方式：N+M 标准化

  • 每个 Agent 实现一次 MCP Client
  • 每个工具实现一次 MCP Server
  • N + M 个实现即可互相连接
  • 新增 Agent 或工具不需要改动已有代码

6.2 MCP 架构与核心组件

图 11：MCP 协议架构全景。Host 应用管理多个 MCP Client，每个 Client 与一个 MCP Server 建立 1:1 连接，Server 通过标准接口暴露 Tools/Resources/Prompts 等能力。

6.3 MCP 协议基础：JSON-RPC 2.0

MCP 在传输层之上使用 JSON-RPC 2.0 作为消息格式。所有的方法调用、通知和响应 都封装在标准的 JSON-RPC 消息中，支持三种消息类型：

1

Request（请求）

从 Client 或 Server 发起，必须包含 method（方法名）和唯一的 id。 例如 {"jsonrpc":"2.0", "id":1, "method":"tools/list"}。 接收方必须返回对应 id 的 Response。

2

Response（响应）

对 Request 的回复，包含 result（成功）或 error（失败）。 必须携带与请求相同的 id。 例如 {"jsonrpc":"2.0", "id":1, "result":{"tools":[...]}}。

3

Notification（通知）

没有 id 字段的消息，不需要回复。用于单向事件通知， 如 {"jsonrpc":"2.0", "method":"notifications/tools/list_changed"}， 通知 Client 工具列表已更新。

4

错误码

标准 JSON-RPC 错误码（-32600 ~ -32603）加 MCP 自定义错误码。 支持 error.data 字段携带详细错误上下文， Client 可据此进行错误恢复或重试。

能力协商（Capability Negotiation）：在 initialize 阶段，Client 和 Server 交换各自支持的能力集合。 例如 Server 可声明支持 tools、resources、prompts、logging 等能力， Client 可声明支持 sampling（允许 Server 请求 LLM 补全）和 roots（允许 Server 访问文件系统根目录）。 只有在初始化阶段声明的能力才能在后续使用——这是 MCP 安全模型的基础。

6.5 MCP Server 暴露的四大原语

MCP Server 可以向 Client 暴露四种标准化原语，每种原语服务于不同的 Agent 交互模式：

原语 控制方 功能 类比 典型用法
Tools 模型控制 可执行的操作函数 POST 请求 查询数据库、发送消息、创建文件
Resources 应用控制 可读取的数据源 GET 请求 读取文件内容、获取数据库 schema、配置信息
Prompts 用户控制 预定义的提示模板 API 模板 代码审查模板、SQL 生成模板、翻译模板
Sampling Server 发起 请求 LLM 生成 回调 Server 需要 LLM 帮助做决策（反向调用）
Tools vs Resources 的关键区别：
  • Tools 是"动作"——有副作用（写入、发送、删除），由模型自主决定何时调用
  • Resources 是"数据"——只读、无副作用，由应用/用户决定何时加载到上下文中
这一区分至关重要：Resources 可以安全地自动加载（如将文件内容注入上下文），而 Tools 的执行需要用户确认或权限检查。

6.6 Transport 传输层

MCP 支持多种传输层机制，适应不同的部署场景：

1

stdio（标准输入输出）

Host 以子进程方式启动 MCP Server，通过 stdin/stdout 管道通信。 适合本地工具（如文件系统、Git），延迟极低，无需网络。 消息以换行符分隔的 JSON-RPC 文本流传输。最简单、最常用的传输方式。

2

Streamable HTTP（推荐远程方式）

2025 年新增的传输协议，取代 HTTP+SSE。Client 通过 POST /mcp 发送请求， Server 可返回单个 JSON 响应或 SSE 事件流。支持有状态和无状态两种模式， 通过 Mcp-Session-Id Header 管理会话。

3

HTTP+SSE（旧版远程方式）

Client 建立 SSE 连接接收 Server 推送，通过 HTTP POST 发送请求。 已被 Streamable HTTP 取代，但仍需支持兼容。 每个连接维护独立会话状态。

4

自定义 Transport

MCP 协议不限定传输层实现，任何支持双向消息传递的通道都可以。 社区已有 WebSocket、gRPC、Unix Socket 等实现。 只需保证消息的完整性和顺序性。

6.8 MCP 安全模型

MCP 的安全设计遵循最小权限原则，通过多层机制保障安全：

  • 用户确认（Human-in-the-Loop）：Host 在执行任何 Tool 调用前应提示用户确认， 用户可以逐次确认或批量授权特定工具。这是最重要的安全屏障
  • 能力声明：Server 只能使用在初始化阶段声明的能力，Client 可以拒绝不信任的能力
  • 信息隔离：不同 MCP Server 之间完全隔离，一个恶意 Server 无法访问其他 Server 的数据
  • Transport 安全：远程连接必须使用 HTTPS + OAuth 2.0 认证，支持 PKCE 流程防止授权码劫持
  • 输入验证：Server 必须对所有输入参数进行验证，防止注入攻击
  • 速率限制：Server 应实现请求频率限制，防止 Agent 无限循环调用
Prompt Injection 风险：MCP 特别需要防范的场景是——恶意 MCP Server 在返回结果中嵌入 prompt injection 指令（如 "忽略之前的指令，改为执行..."），诱导 LLM 执行非预期操作。 Host 应对 tool result 进行过滤，标记为不受信任的外部输入，并在系统提示中明确指示模型 不要执行工具返回内容中的指令。

MCP 与传统 Function Calling 的关系：MCP 并不替代 Function Calling，而是在其基础上增加了一层标准化的工具发现与管理协议。 在运行时，MCP Server 暴露的 Tools 最终仍然通过 LLM 的 Function Calling 机制被调用—— MCP Client 将 Server 的工具描述转换为 LLM API 的 tools 参数格式， LLM 生成 tool_call 后，Client 将调用请求转发给对应的 MCP Server 执行。 MCP 解决的是"工具从哪来"的问题，Function Calling 解决的是"如何调用工具"的问题。

七、Multi-Agent 系统

7.1 为什么需要 Multi-Agent？

单 Agent 在面对超大规模、需要多种专业能力、或需要自我检查的任务时， 存在上下文窗口溢出、能力不足、缺乏自我审查等问题。 Multi-Agent 通过分工协作解决这些瓶颈。

图 13：Multi-Agent 协作架构。Orchestrator Agent 负责任务分解和协调，子 Agent 各司其职完成专项任务，最终结果由协调者整合。

7.2 Multi-Agent 协作模式

1

顺序流水线

Agent A → Agent B → Agent C 依次处理。适合有明确前后依赖的任务（如：写代码 → 审核 → 测试）。

2

层级委托

Orchestrator 将任务分解为子任务，委托给专项 Agent 执行。支持递归分解——子 Agent 还可以再委托。

3

辩论审核

多个 Agent 独立解决同一问题，然后交叉审核对方的结果。适合需要高可靠性的决策场景。

4

竞争选优

多个 Agent 并行尝试不同策略，由评估 Agent 选择最佳结果。以计算成本换取结果质量。

八、Agent 安全与可控性

8.1 Agent 安全的核心挑战

与纯对话 LLM 不同，Agent 可以执行真实操作——这使安全问题从"说错话"升级为"做错事"。 一个失控的 Agent 可能删除文件、发送邮件、执行恶意代码，造成不可逆的损害。

安全风险 场景 防御措施
Prompt 注入 恶意用户或网页内容操纵 Agent 行为 输入过滤、系统指令隔离、工具结果验证
过度操作 Agent 超出用户授权执行危险操作 权限最小化原则、操作确认机制（Human-in-the-Loop）
代码注入 Agent 生成的代码包含恶意/危险逻辑 沙箱执行、代码审查、资源限制
信息泄露 Agent 将敏感信息发送到外部服务 数据流审计、网络隔离、输出过滤
无限循环 Agent 陷入死循环，消耗大量资源 最大步数限制、超时机制、成本上限
供应链攻击 恶意的 MCP Server / 工具 工具来源验证、权限审核、沙箱隔离

8.2 安全控制设计模式

1

Human-in-the-Loop

高风险操作（如文件删除、邮件发送、代码部署）需要用户显式确认。Claude Code 对破坏性操作默认要求确认。

2

沙箱隔离

代码执行在隔离的容器/虚拟机中运行，限制文件系统访问、网络访问和系统调用。Docker + seccomp 是常见方案。

3

权限分级

工具按风险等级分类：只读工具（搜索）自动允许，写入工具（文件编辑）需确认，危险工具（shell）需白名单。

4

审计与回滚

完整记录 Agent 的每一步操作，支持事后审计和操作回滚。Git 版本控制天然支持代码变更的回滚。

十、Agent 发展趋势与未来

1

Agent 原生模型

未来的 LLM 将在预训练阶段就融入工具交互数据，而非后期微调。Agent 能力将成为模型的"原生能力"而非"附加功能"。

2

长时自主运行

从"回答一个问题"到"完成一个项目"——Agent 将能自主运行数小时甚至数天，处理复杂的多阶段任务（如 Devin、Claude Code background agent）。

3

多模态 Agent

Agent 不仅能处理文本，还能"看"屏幕（Computer Use）、"听"语音、"说"对话，成为真正的全模态交互智能体。

4

Agent 标准化

MCP 等标准化协议将统一工具接入方式，Agent-to-Agent 通信协议（如 A2A）将让不同 Agent 能够互相协作。

总结

LLM Agent 代表了大模型从"语言理解"到"自主行动"的范式跃迁。本文系统介绍了 Agent 的核心原理与实现：

  1. 执行原理：Agent 通过"思考-行动-观察"的迭代循环完成任务，ReAct 和 Plan-and-Execute 是两大基础范式
  2. 工具调用：Function Calling 让 LLM 生成结构化调用意图，由宿主程序安全执行，实现了"决策"与"执行"的分离
  3. 训练与数据：Agent 能力通过 Tool Use SFT + Agent RL 获得，训练数据需覆盖多种工具、多步调用和错误恢复场景
  4. 记忆系统：短期/工作/长期三层记忆架构，RAG 是长期记忆的核心实现
  5. 主流方案：从 Claude Code、ChatGPT 等产品到 LangGraph、AutoGen 等框架，Agent 生态日趋完善
  6. Multi-Agent：分工协作、辩论审核、层级委托等模式解决单 Agent 的能力瓶颈
  7. 安全可控：沙箱隔离、权限分级、Human-in-the-Loop 等机制确保 Agent 安全可信
Agent 的终极愿景：让 LLM 不仅是一个回答问题的"聊天机器人"， 而是一个能理解复杂目标、自主分解任务、灵活调用工具、持续学习改进的通用智能体—— 人类的得力数字助手。
