从字符到子词 —— 大语言模型的第一道关卡
BPE WordPiece Unigram SentencePiece Byte-level BPE Tiktoken

引言：为什么分词是大模型的基石

大语言模型（LLM）不直接处理原始文本，而是将文本转换为离散的 token 序列后送入 Transformer。 分词器（Tokenizer）决定了模型"看到"什么——它是文本与模型之间的桥梁，直接影响模型的词表大小、 序列长度、训练效率和多语言能力。

核心权衡： 词表越大，每个 token 承载的语义越丰富、序列越短，但 Embedding 层参数越多； 词表越小，Embedding 层轻量，但同一文本被拆成更多 token，增加计算量和上下文消耗。 现代 LLM 的词表通常在 32K ~ 150K 之间。
图 1：分词器在 LLM 推理流程中的位置。文本首先经过 Tokenizer 分词并映射为整数 ID，再通过 Embedding 层转为向量送入 Transformer。

二、BPE 分词器 —— 原理详解

2.1 历史背景

BPE（Byte Pair Encoding）最初由 Philip Gage 于 1994 年提出，是一种简单的数据压缩算法。 2015 年，Sennrich 等人将其引入 NLP 用于机器翻译的子词分割。 2019 年，Radford 等人在 GPT-2 中将 BPE 与 Byte-level 编码结合，使其成为 LLM 的标准分词方案。

BPE 的核心直觉： 频繁出现的字符组合应该被视为一个整体（合并为一个 token），而罕见的词可以被拆分为更小的、有意义的子词片段。 这种"频率驱动的自底向上合并"策略天然实现了词表大小与表达能力之间的平衡。

Step 3：重新统计，(est, </w>) 频率 = 9，最高。

Merge #3： est + </w> → est</w>
语料更新: newest → n e w est</w>, widest → w i d est</w>

Merge #4： l + o → lo
语料更新: low → lo w </w>, lower → lo w e r </w>

如此往复，每次合并都将最频繁的相邻对融合为新 token，直到词表达到目标大小（如 32,000）。

3.3 BPE 训练的核心算法

图 5：BPE 训练算法的完整流程图。核心循环是：统计 → 找最高频对 → 合并 → 重复，直到词表达到目标大小。

3.4 伪代码

function train_BPE(corpus, vocab_size):
    vocab ← 所有语料中出现的字符集合
    word_freqs ← 统计语料中每个词的频率
    splits ← { word → 字符列表  for word in word_freqs }
    merges ← []

    while |vocab| < vocab_size:
        pair_counts ← {}
        for word, freq in word_freqs:
            symbols ← splits[word]
            for i in range(len(symbols) - 1):
                pair_counts[(symbols[i], symbols[i+1])] += freq

        best_pair ← argmax(pair_counts)
        merges.append(best_pair)
        vocab.add(best_pair[0] + best_pair[1])

        // 在所有词中应用此合并
        for word in splits:
            replace all adjacent (best_pair[0], best_pair[1]) with merged token

    return vocab, merges

四、BPE 编码过程 —— 对新文本分词

4.1 编码算法

训练完成后，我们得到一个有序的合并规则列表（merges）。对新文本编码时，按照合并规则的 学习顺序 依次尝试应用：

  1. 将输入词拆分为字符序列
  2. 按 merges 中的顺序，检查当前序列中是否存在该 pair
  3. 如果存在，执行合并；如果不存在，跳过
  4. 遍历完所有 merge 规则后，当前序列就是最终分词结果
  5. 将每个 token 映射到词表中的整数 ID

4.2 编码示例

假设经过训练，我们的 merges 列表（按学习顺序）为：

Merges（有序）： ① (e, s) → es   ② (es, t) → est   ③ (est, </w>) → est</w>   ④ (l, o) → lo   ⑤ (lo, w) → low   ⑥ (n, e) → ne   ⑦ (ne, w) → new   ⑧ (new, est</w>) → newest</w>   …

五、UTF-8 字符编码 —— 理解 Byte-level BPE 的前置知识

要理解 Byte-level BPE 为什么以"字节"而非"字符"为基本单元，首先需要深入理解 UTF-8 编码——当今互联网和大模型训练数据最主流的文本编码方式。

5.1 从 ASCII 到 Unicode：字符编码简史

计算机只能处理数字。要存储和传输文本，必须建立"字符 → 数字"的映射关系，这就是字符编码。

图 7：字符编码的演化。Unicode 统一了全球字符集，UTF-8 是其最流行的编码实现方案。
关键区分： Unicode 是一张"字符 → 编号"的映射表（如 "你" → U+4F60），只定义了编号（Code Point）； UTF-8 是一种"编号 → 字节序列"的编码规则，决定了 U+4F60 在计算机中具体存储为哪些字节。 此外还有 UTF-16、UTF-32 等编码方案，但 UTF-8 因其兼容 ASCII 和节省空间而成为互联网的事实标准。

5.2 UTF-8 编码规则详解

UTF-8 是一种变长编码，使用 1~4 个字节表示一个 Unicode 字符。核心设计原则是： 常用字符用更少的字节，罕见字符用更多的字节——这正是信息论中"频率越高，编码越短"的最优编码思想。

Unicode 范围 字节数 字节模板（二进制） 可用 bit 数 覆盖字符
U+0000 ~ U+007F 1 字节 0xxxxxxx 7 bit ASCII（英文字母、数字、基础标点）
U+0080 ~ U+07FF 2 字节 110xxxxx 10xxxxxx 11 bit 拉丁扩展、希腊、西里尔、阿拉伯
U+0800 ~ U+FFFF 3 字节 1110xxxx 10xxxxxx 10xxxxxx 16 bit 中文、日文、韩文、大多数常用字符
U+10000 ~ U+10FFFF 4 字节 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx 21 bit Emoji、古文字、数学符号、罕见文字
设计精妙之处： 每个字节的前缀位（0 / 110 / 1110 / 11110 / 10）使得 UTF-8 具有自同步性—— 从任意字节位置开始，都能明确判断这是一个字符的首字节还是后续字节，不会产生歧义。 这种设计也意味着 ASCII 文本的 UTF-8 编码与原始 ASCII 完全相同（向后兼容）。

5.5 UTF-8 对分词的深远影响

理解 UTF-8 之后，我们可以清晰地看到它如何影响 Byte-level BPE 的行为：

1

英文天然高效

英文字母是 1 字节 = 1 个基础 token。经过 BPE 合并后，常见英文单词通常成为 1 个 token（如 "the"、"and"）。

2

中文先天 3 倍开销

每个中文字符占 3 字节 = 3 个基础 token。BPE 合并后常见字可被合并为 1 个 token，但罕见字仍需 2~3 个 token。

3

Emoji 开销最大

Emoji 占 4 字节，复合 Emoji（如 👨‍👩‍👧‍👦）由多个 Code Point + ZWJ 连接，可能需要 10+ 字节。

4

词表决定压缩效率

词表越大，越多的多字节序列被合并为单个 token。这就是为什么 Qwen（151K 词表）比 LLaMA-2（32K 词表）对中文更高效。

图 9：中英文混合文本的 UTF-8 字节分解。英文 1:1 映射，中文 1:3 映射，这正是中文"膨胀率"更高的根本原因。

5.6 常见编码对比

编码方案 字节长度 ASCII 兼容 适用场景
UTF-8 1~4 字节（变长） ✅ 完全兼容 互联网、LLM 训练数据、大多数文件
UTF-16 2 或 4 字节 ❌ Windows 内部、Java/JavaScript 字符串
UTF-32 固定 4 字节 ❌ 内部处理（简单但浪费空间）
GBK 1~2 字节 ✅（单字节部分） 中文 Windows 传统环境
为什么 Byte-level BPE 选择 UTF-8： (1) UTF-8 是互联网文本的主流编码（占比 >98%），训练数据几乎都是 UTF-8； (2) ASCII 兼容意味着英文处理零开销； (3) 变长编码使得字节值域固定为 0~255，初始词表大小恒定为 256——无论训练数据包含多少种语言。

六、Byte-level BPE —— 现代 LLM 的标准方案

6.1 从字符到字节

有了 UTF-8 的知识铺垫，我们现在可以更清晰地理解 Byte-level BPE 的设计动机。 标准 BPE 的初始词表是 Unicode 字符集中出现的字符，不同语言的字符集差异很大。 Byte-level BPE（GPT-2 提出）将基本单元从字符降低到 UTF-8 字节（0x00~0xFF, 共 256 个）， 初始词表固定为 256 个字节 token。

图 10：字符级 BPE 与 Byte-level BPE 的区别。Byte-level BPE 以 UTF-8 字节为最小单元，天然支持所有语言和符号。

6.2 Byte-level BPE 的工作流程

1

字节编码

将原始文本转换为 UTF-8 字节序列。每个字节值 0~255 对应一个基础 token。

2

BPE 合并

在字节序列上执行标准 BPE 训练/编码流程。高频字节对逐步合并为更大的 token。

3

多字节 Token

常见字（如英文单词、中文常用字）会被合并为单个 token；罕见字仍可回退到字节级别。

4

解码还原

将 token ID 映射回字节序列，再通过 UTF-8 解码恢复原始文本，无损还原。

八、工程实践中的关键细节

8.1 Pre-tokenization（预分词）

在执行 BPE 之前，文本通常先通过预分词（Pre-tokenization）将文本切分为"词"级别的块， BPE 只在每个块内部进行合并，不会跨词边界合并。这防止了不合理的跨词 token 出现。

GPT-2/4 的预分词正则：
r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+"""
将文本按空格、标点、数字等边界切分为独立的预分词块，BPE 在各块内独立运行。

8.2 特殊 Token

除了 BPE 学到的 token 之外，实际词表还包含若干手动添加的特殊 token：

特殊 Token用途示例
<|endoftext|>文档/对话结束标记GPT 系列
<s> / </s>序列开始/结束标记LLaMA、T5
<|im_start|> / <|im_end|>对话角色边界标记ChatML 格式
<pad>填充（对齐 batch）BERT、T5
<unk>未知 token（Byte-level BPE 不需要）传统模型

8.3 词表大小的选择

小

32K（LLaMA-1/2）

Embedding 参数少，但中文等需要更多 token 表示，序列更长，推理更慢。

中

100K（GPT-4）

多语言覆盖好，单次推理的 token 数适中。是目前主流的平衡点。

大

128K~150K（LLaMA-3、Qwen）

多语言和代码压缩率高，但 Embedding 层参数较大（约 0.5~1B 参数）。

趋势

越来越大

更大的词表意味着同一文本用更少的 token 表示，有效增加了上下文窗口的信息密度。

8.4 Tiktoken —— 高性能 BPE 实现

OpenAI 开源的 Tiktoken 是一个用 Rust 编写的高性能 BPE 实现，比 HuggingFace Tokenizers 快 3~6 倍。LLaMA-3、GPT-4 等模型均使用 Tiktoken 作为分词器后端。

Tiktoken 优势

  • Rust 实现，极致性能
  • 支持 Byte-level BPE
  • 正则表达式预分词
  • API 极简，几行代码即用

需注意

  • 不支持 Unigram / WordPiece
  • 自定义词表需要自己构建 merge 文件
  • 不提供训练功能（只做编码）
  • 社区工具链不如 HuggingFace 丰富

九、分词质量对模型性能的影响

9.1 Fertility（膨胀率）

Fertility 指一个词平均被拆分为多少个 token。膨胀率越高，说明分词器对该语言的压缩效率越低。 这直接影响了有效上下文长度和推理成本。

图 12：同一中文句子在不同词表大小下的 token 数量对比。128K 词表将中文膨胀率降低了约 57%。

9.2 分词影响总结

1

有效上下文长度

膨胀率高意味着同样的文本消耗更多 token 位置，等效缩短了模型的上下文窗口。

2

推理成本

自回归解码逐 token 生成。token 越多，前向传播次数越多，延迟和成本线性增加。

3

多语言公平性

词表中中文/日文/阿拉伯文 token 占比低时，这些语言的膨胀率远高于英文，导致"隐性不公平"。

4

语义边界

不合理的分词可能切断词义（如 "transformer" → "trans" + "former"），影响模型理解。

十、前沿趋势与展望

10.1 当前趋势

  • 词表持续增大：从 GPT-2 的 50K 到 Qwen 的 150K+，更大的词表提供更好的压缩率和多语言支持。
  • Byte-level BPE 成为主流：以 UTF-8 字节为基础单元已成为行业共识，彻底消除 OOV 问题。
  • 训练数据决定词表质量：分词器训练数据中各语言的比例直接决定了各语言的压缩效率。
  • 高性能实现：Tiktoken（Rust）、HuggingFace Tokenizers（Rust）等高性能实现成为标配。

10.2 探索方向

🔬

Token-free 模型

如 MegaByte、ByT5，直接在字节级别建模，完全跳过分词器。目前性能仍有差距，但方向明确。

🔬

动态分词

根据领域/语言动态切换分词策略。如代码场景用代码优化词表，自然语言场景用通用词表。

🔬

多粒度 Token

在同一模型中支持不同粒度的 token（字节、字符、子词、词），根据上下文自适应选择。

🔬

语义感知分词

传统 BPE 仅基于频率统计，未来可能结合语义信息指导合并，使 token 边界与语义边界对齐。

总结

一句话总结：BPE 通过"统计频率 → 合并最高频对 → 迭代"的简洁策略，在词表大小与表达能力之间 找到了最优平衡，其 Byte-level 变体更是成为了现代 LLM 的事实标准。
图 13：BPE 的演化历程——从 1994 年的压缩算法到现代 LLM 的标准分词方案。

分词器虽然在大模型架构中常被忽视，但它是整个系统的基石。一个好的分词器能有效提升模型的多语言能力、 降低推理成本、延长有效上下文。随着词表不断增大和 Byte-level BPE 的普及，分词技术正在变得越来越成熟， 但关于"是否需要分词器"的讨论也在持续——Token-free 模型或许代表了更远的未来方向。
