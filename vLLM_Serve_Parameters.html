一、整体架构概览

vLLM 是一个高性能大语言模型推理引擎，vllm serve 命令启动一个 OpenAI 兼容的 HTTP API 服务。 其核心设计包括：PagedAttention（分页 KV 缓存管理）、Continuous Batching （连续批处理）、Prefix Caching（前缀缓存）、Speculative Decoding（投机解码）等。

图 1：vLLM Serve 参数分组架构图。从前端到底层分为 Frontend、Scheduler、Model/Cache/Parallel、MultiModal/LoRA/Compilation 等模块。
核心理解：vLLM 的吞吐量 = 每次迭代处理的 token 数 × 迭代频率。 调优的本质是 (1) 让 GPU 每步处理更多 token（调大 batch、加并发）、 (2) 减少每步的无效开销（CUDA Graph、async 调度）、 (3) 合理分配显存（更多 KV cache = 更多并发能力）。

二、ModelConfig — 模型配置

控制模型加载、精度、序列长度等基础行为。对显存预算和推理精度有直接影响。

--model MODEL str 默认: Qwen/Qwen3-0.6B

HuggingFace 模型名或本地路径。支持原始权重、GPTQ、AWQ、FP8 量化格式。

所有场景 必须指定的参数。

--dtype {auto,half,float16,bfloat16,float,float32} str 默认: auto 影响: 显存 / 精度

auto 时 FP32/FP16 模型用 FP16，BF16 模型用 BF16，FP8 模型用 FP8。 手动指定 half 推荐用于 AWQ 量化模型。BF16 精度范围更大但精度略低于 FP16。

量化模型 混合精度

--max-model-len MAX_MODEL_LEN int | str 默认: 模型 config 中的 max_position_embeddings 影响: 显存 / 并发

模型最大序列长度（输入 + 输出之和）。直接决定 KV 缓存预分配大小。 支持人类可读格式：32k=32000，128K=131072，-1=自动适配显存。

设过大会大幅减少可用 KV cache → 并发数下降。 如果 90% 的请求 <8K token，设 8192 比 131072 能多承载 16 倍并发。

长上下文 高并发 显存受限

--quantization QUANTIZATION, -q str 默认: None（自动检测） 影响: 显存 / 速度 / 精度

量化方式。自动从模型 config 中检测，也可手动指定。常见值：

方法精度损失显存节省速度说明
None (FP16/BF16)无基线基线无量化
fp8极小~50%快（H100+）需 Ada/Hopper GPU
gptq小~75%(4bit)中需预量化模型
awq小~75%(4bit)快推荐配 half dtype
bitsandbytes中~75%较慢动态量化

显存受限 大模型单卡

--enforce-eager flag 默认: False 影响: 启动速度 / 推理速度

强制使用 eager 模式，禁用 CUDA Graph。调试时有用，生产环境不建议开启。 CUDA Graph 通过预录制 GPU 操作序列来消除 Python/CUDA kernel launch 开销， 对 decode 阶段（小 batch）加速显著。

调试 自定义算子

--trust-remote-code flag 默认: False

允许执行模型仓库中的自定义 Python 代码。大部分非标准架构模型（如 Qwen 系列、DeepSeek 系列）需要开启。

安全风险：恶意模型仓库可能在自定义代码中嵌入恶意逻辑。仅在信任的模型来源上使用。

Qwen/DeepSeek/ChatGLM等

--served-model-name NAME [NAME ...] str 默认: 同 --model

API 中返回的模型名称。支持多个别名，第一个为主名称。用于在 API 响应和 Prometheus 指标中呈现。

--seed SEED int 默认: 0

随机种子。在多卡 TP 模式下确保各 worker 采样一致。设为固定值可复现结果。

--tokenizer-mode {auto,hf,slow,mistral,deepseek_v32} str 默认: auto

分词器模式。auto 优先使用快速分词器。slow 强制使用慢速分词器（某些特殊模型需要）。 deepseek_v32 使用 DeepSeek 定制分词器。

--generation-config {auto,vllm,path} str 默认: auto

auto 从模型目录加载 generation_config.json（包含默认 temperature、top_p 等）。 vllm 忽略模型的生成配置，使用 vLLM 默认值。也可指定自定义配置目录路径。

--override-generation-config JSON dict 默认: {}

覆盖生成参数。例如 --override-generation-config '{"temperature": 0.7}'。 与 --generation-config auto 配合时，覆盖项与默认项合并。

--model-impl {auto,vllm,transformers} str 默认: auto

模型实现方式。auto 优先用 vLLM 内置实现（性能最优），回退到 Transformers。 当 vLLM 尚未适配某模型时可切到 transformers（性能略低但兼容性更好）。

--kv-cache-dtype {auto,fp8,fp8_e4m3,fp8_e5m2,bfloat16,float16} str 默认: auto 影响: 显存 / 精度

KV 缓存数据类型。auto 使用模型精度。设为 fp8 可将 KV 缓存大小减半， 在 H100/H200 等 Hopper GPU 上几乎无精度损失。显存受限时最有效的优化手段之一。

长上下文 高并发 H100/H200

三、CacheConfig — KV 缓存配置

KV 缓存是 vLLM 最核心的资源。更多 KV 缓存 = 更多并发序列 = 更高吞吐。

图 2：GPU 显存分配。gpu-memory-utilization 控制可用于 KV 缓存的显存比例。
--gpu-memory-utilization GPU_MEMORY_UTILIZATION float [0, 1] 默认: 0.90 影响: 并发 / 稳定性

GPU 显存使用上限比例。vLLM 启动时先加载模型权重，然后将剩余显存（在此上限内）全部分配给 KV 缓存。

值适用场景风险
0.85与其他进程共享 GPUKV cache 较少，并发受限
0.90默认值，适合大多数场景低
0.95独占 GPU，追求最大并发接近 OOM 边界
0.98极限压榨（不推荐）可能因碎片化 OOM
--enable-prefix-caching flag 默认: None（自动） 影响: prefill 速度

启用前缀缓存。当多个请求共享相同的系统提示词或前缀时， KV 缓存可复用，避免重复计算。适合系统提示词固定的 API 服务。

何时有用：所有请求使用相同的 system prompt（如 ChatBot 场景），命中率高时 prefill 速度提升数倍。
何时无用：每个请求输入完全不同（如视频理解），命中率为 0%，开启反而有管理开销。

ChatBot API RAG 服务

--block-size BLOCK_SIZE int 默认: 自动（通常 16）

PagedAttention 的块大小。每个 KV cache 块存储的 token 数。较大值减少块管理开销但增加内部碎片。 一般不需要手动调整。

--kv-cache-memory-bytes SIZE int | str 默认: None（自动）

直接指定 KV 缓存大小（字节），比 gpu-memory-utilization 更精确。 设置后忽略 utilization。支持 10G、50G 等格式。

精确控制显存 多实例共享 GPU

--prefix-caching-hash-algo {sha256,xxhash,...} str 默认: sha256

前缀缓存的哈希算法。xxhash 更快但非密码学安全（多租户场景有碰撞风险）。 单租户场景可用 xxhash 提升缓存查找速度。

--calculate-kv-scales flag 默认: False

FP8 KV cache 时动态计算缩放因子（而非使用 checkpoint 中的静态值）。 可能提升精度但有少量计算开销。

四、SchedulerConfig — 调度器配置

调度器决定每次 GPU 迭代处理哪些请求、多少 token。对吞吐影响最直接。

--max-num-batched-tokens MAX_NUM_BATCHED_TOKENS int | str 默认: 自动（通常 = max_model_len 或 2048） 影响: 吞吐 / GPU利用率

单次调度迭代中允许处理的最大 token 总数。这是影响吞吐的最重要参数之一。

  • 设太小（如 4096）→ GPU 每步只处理少量 token，算力空闲
  • 设太大（如 131072）→ 长 prefill 独占 GPU，decode 请求被阻塞，延迟抖动大
  • 推荐值：16384~32768（平衡吞吐和延迟）
经验法则：对于 decode-heavy 场景（高并发短输出），设大到 32K+； 对于 prefill-heavy 场景（少量长输入），配合 chunked-prefill 使用，设 8K~16K。

吞吐优化 所有场景

--max-num-seqs MAX_NUM_SEQS int 默认: 自动（通常 256） 影响: 并发 / 延迟

单次迭代中允许调度的最大序列数。设大则更多请求同时处理（吞吐高）， 设小则每个请求分到更多计算资源（延迟低）。

高并发 低延迟

--enable-chunked-prefill flag 默认: None（自动） 影响: 延迟稳定性 / TTFT

启用分块预填充。将长 prompt 的 prefill 拆成多个 chunk，与 decode 请求交错执行。

关键好处：防止一个长 prompt（如 10 万 token 的视频输入）独占 GPU 数秒， 导致其他正在 decode 的请求被阻塞。启用后 TTFT 抖动大幅减小。
几乎所有生产环境都应开启，代价极小（极少量调度开销）。

在线服务 多模态 长上下文

--max-num-partial-prefills int 默认: 1

同时进行分块预填充的最大序列数。增大可提升 prefill 并行度， 但多个长 prefill 同时进行会挤占 decode 带宽。

--max-long-partial-prefills int 默认: 1

同时进行分块预填充的"长"序列最大数量。长序列的判定阈值由 --long-prefill-token-threshold 控制。设 < max-num-partial-prefills 可让短请求"插队"到长请求前面。

--async-scheduling flag 默认: None（自动开启） 影响: 吞吐 / GPU利用率

异步调度。调度器在 GPU 执行当前 batch 时并行准备下一个 batch， 消除调度延迟导致的 GPU 空闲气泡。推荐开启。

高吞吐 所有场景

--scheduling-policy {fcfs,priority} str 默认: fcfs

fcfs（先来先服务）按到达顺序调度。priority 支持按优先级调度（低值优先）， 通过 API 请求中的 priority 字段指定。

优先级队列 VIP 用户优先

--disable-chunked-mm-input flag 默认: False

禁止将多模态 token（如图像 token）拆分到不同 chunk 中。 开启后保证一个图像的所有 token 在同一轮处理，避免部分调度导致的问题。

多模态模型

五、ParallelConfig — 并行策略配置

控制多卡推理的并行模式。vLLM 支持张量并行（TP）、流水线并行（PP）、数据并行（DP）和专家并行（EP）。

图 3：四种并行策略对比。单模型装不下用 TP/PP，装得下优先用 DP 扩展吞吐。
--tensor-parallel-size TP, -tp TP int 默认: 1 影响: 显存 / 延迟

张量并行度。将每一层的权重矩阵按列/行切分到多张 GPU 上。

场景推荐 TP说明
27B FP8, 单卡 H2001单卡装得下，不需要 TP
70B FP16, 2×H100270B FP16 ≈ 140GB，需要 2 卡
405B FP8, 8×H1008405B FP8 ≈ 200GB+，需要 8 卡
TP 越大，卡间通信开销越大（每层 2 次 AllReduce）。 能用 1 就不用 2——优先用量化降显存需求，而非加 TP。
--pipeline-parallel-size PP, -pp PP int 默认: 1

流水线并行度。将模型层分到不同 GPU 组。通信量小于 TP（仅传隐状态而非全矩阵）， 适合跨节点部署。但存在气泡效应，需要较大 batch 填满流水线。

跨节点 超大模型

--data-parallel-size DP, -dp DP int 默认: 1 影响: 吞吐

数据并行度。每个 DP rank 运行完整模型副本，请求在 rank 间负载均衡。 吞吐线性增长，无通信开销（除 MoE EP 场景）。

例：4×H200 跑 27B FP8，设 -dp 4 吞吐 ≈ 4 × 单卡吞吐。

多卡高吞吐 模型单卡可装下时

--enable-expert-parallel, -ep flag 默认: False

启用专家并行。仅用于 MoE 模型（如 Qwen3-235B-A22B、DeepSeek-V4 等）， 将路由专家分散到多张 GPU 上。通常与 DP 联合使用（DP+EP）。

MoE 模型 DeepSeek/Qwen3 MoE

--all2all-backend str 默认: allgather_reducescatter

MoE 专家并行的 All-to-All 通信后端。可选 deepep_high_throughput、 deepep_low_latency（DeepSeek 开源内核）、flashinfer_nvlink_* 等。 NVLink 互联时 flashinfer_nvlink_two_sided 性能最优。

--decode-context-parallel-size DCP, -dcp DCP int 默认: 1

解码上下文并行度。将 KV 缓存沿序列长度维度拆分到多张 GPU， 降低单卡 KV cache 显存需求。适合超长上下文（如 1M token）场景。 需要 TP > 1 且 TP 能被 DCP 整除。

百万级上下文

六、MultiModalConfig — 多模态配置

控制图像、视频等多模态输入的处理行为。对多模态模型的推理效率和显存至关重要。

--media-io-kwargs JSON dict 默认: {} 影响: 视觉token数 / 速度

传递给媒体处理器的额外参数。最重要的用途是控制视频帧数：

# 提取全部帧（慢！10秒视频可能产生 10万+ 视觉 token）
--media-io-kwargs '{"video": {"num_frames": -1}}'

# 固定采样 64 帧（推荐大多数场景）
--media-io-kwargs '{"video": {"num_frames": 64}}'

# 短视频场景，32 帧足够
--media-io-kwargs '{"video": {"num_frames": 32}}'
性能陷阱：num_frames: -1 是视频推理最常见的性能杀手。 全帧提取时视觉 token 数随视频时长线性增长，prefill 时间可达数十秒。

视频理解

--mm-processor-kwargs JSON dict 默认: None 影响: 视觉token数

传递给模型图像/视频处理器的参数，覆盖 AutoProcessor 的默认配置。常用于控制图像分辨率：

# 限制最大像素数（降低高分辨率图像的 token 数量）
--mm-processor-kwargs '{"max_pixels": 1003520}'

# Phi-3-Vision 示例：控制裁剪数量
--mm-processor-kwargs '{"num_crops": 4}'

图像理解 文档OCR

--limit-mm-per-prompt JSON dict 默认: 每种模态 999 影响: 显存 / 安全

每个请求中各模态输入的最大数量。防止用户发送过多图像/视频导致 OOM。

# 每个请求最多 1 个视频、5 张图像
--limit-mm-per-prompt '{"video": 1, "image": 5}'

# 高级格式：同时限制数量和分辨率
--limit-mm-per-prompt '{"video": {"count": 1, "num_frames": 32}, "image": {"count": 5, "width": 512, "height": 512}}'

多模态API服务 安全防护

--video-pruning-rate RATE float [0, 1) 默认: None

视频 token 剪枝率。例如设为 0.5 则丢弃 50% 的视觉 token，在质量和速度之间取得折中。 基于 Efficient Video Sampling 策略，优先保留信息量高的 token。

视频理解加速

--mm-encoder-tp-mode {weights,data} str 默认: weights

多模态编码器的 TP 模式。weights 按标准 TP 切分权重； data 每个 TP rank 持有完整权重但切分 batch 数据（类似编码器级别的 DP）。 批量图像/视频较多时 data 模式可能更快。

--language-model-only flag 默认: False

禁用所有多模态输入，将多模态模型当作纯语言模型使用。不加载视觉编码器，节省显存。

仅用语言能力

七、SpeculativeConfig — 投机解码配置

投机解码通过"小模型猜测、大模型验证"的方式加速自回归生成。

图 4：投机解码原理。Draft 模型快速猜测 k 个 token，主模型一次验证。
--speculative-config JSON dict 默认: None（不使用投机解码） 影响: 延迟 / 吞吐

投机解码完整配置。常用配置示例：

# 使用 Qwen3.5 内置 MTP 头（最轻量，无需额外模型）
--speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'

# 使用独立 Draft 模型
--speculative-config '{"model":"Qwen/Qwen3-0.6B","num_speculative_tokens":3}'

# 使用 N-gram 匹配（无模型开销，适合重复性强的文本）
--speculative-config '{"method":"ngram","num_speculative_tokens":3,"ngram_prompt_lookup_max":4}'

关键子参数

参数说明
method投机解码方法：qwen3_next_mtp（MTP头）、ngram、draft_model 等
num_speculative_tokens每步猜测的 token 数量。越大潜在加速越高，但拒绝开销也越大
modelDraft 模型路径（仅 draft_model 方法需要）
何时不该使用投机解码：
1. 高并发场景 — decode 已通过 batching 加速，投机解码的边际收益小
2. 接受率 < 60% — 拒绝开销 > 加速收益，反而降速
3. Prefill 瓶颈场景（如视频输入）— 投机解码只加速 decode 阶段

八、LoRAConfig — LoRA 适配器配置

支持在推理时动态加载/切换多个 LoRA 适配器，实现单基座模型服务多任务。

--enable-lora flag 默认: None

启用 LoRA 支持。开启后可在 API 请求中通过 model 字段指定不同的 LoRA 适配器。

--max-loras MAX_LORAS int 默认: 1

单个 batch 中同时激活的最大 LoRA 数量。多 LoRA 场景下增大此值。

--max-lora-rank {1,8,16,32,64,128,256,320,512} int 默认: 16

允许加载的最大 LoRA 秩。需 ≥ 所有 LoRA adapter 的实际 rank。rank 越大显存占用越多。

--lora-modules NAME=PATH [...] list

预加载 LoRA 模块。格式：--lora-modules chat=/path/to/chat-lora code=/path/to/code-lora。 客户端通过 model: "chat" 指定使用哪个 LoRA。

多任务服务 个性化模型

九、CompilationConfig — 编译与 CUDA Graph

控制 torch.compile 和 CUDA Graph 捕获行为。对启动时间和推理速度有显著影响。

--compilation-config, -cc dict 默认: 自动

编译配置。支持 JSON 格式或点号缩写：

# 完全禁用编译和 CUDA Graph（调试用）
-cc '{"mode": 0}'

# 默认模式：CUDA Graph + 基本编译
-cc '{"mode": 2}'

# 最激进的编译优化（启动慢但推理快）
-cc '{"mode": 3}'

# 简写形式
-cc.mode 3
--performance-mode {balanced,interactivity,throughput} str 默认: balanced 影响: 延迟 vs 吞吐

运行时性能策略：

  • balanced：默认平衡模式
  • interactivity：优化低延迟，更细粒度 CUDA Graph，适合对话场景
  • throughput：优化总吞吐，更大 CUDA Graph + 更激进 batching，适合离线批量处理

在线服务vs离线推理

--gdn-prefill-backend {flashinfer,triton} str 默认: None（自动）

Gated DeltaNet 层的 prefill 计算后端。flashinfer 通常更快， triton 兼容性更好。仅对使用 DeltaNet 架构的模型（如 Qwen3.5）有效。

Qwen3.5 系列

十、LoadConfig — 模型加载配置

--load-format {auto,safetensors,pt,gguf,dummy,...} str 默认: auto

模型权重加载格式。auto 优先使用 safetensors（更快更安全）。 dummy 用随机权重初始化，仅用于性能分析。gguf 支持 GGML 量化格式。

--safetensors-load-strategy {lazy,eager,prefetch} str 默认: lazy

safetensors 加载策略：

  • lazy：内存映射按需加载（本地 SSD 最快）
  • eager：全部读入 CPU 内存再加载（网络文件系统推荐，如 NFS/Lustre）
  • prefetch：预读到 OS page cache，加速后续加载

网络存储 启动加速

--download-dir DIR str 默认: HuggingFace 默认缓存目录

模型下载和缓存目录。适用于从 HuggingFace Hub 下载模型的场景。

十一、OffloadConfig — 权重卸载配置

--cpu-offload-gb GB float 默认: 0（不卸载） 影响: 显存 / 速度

将指定大小的模型权重卸载到 CPU 内存，相当于虚拟扩展 GPU 显存。 例如 24GB GPU 设 10，等效于 34GB GPU。 需要高速 CPU-GPU 互联（PCIe 4.0/5.0 或 NVLink），否则推理速度大幅下降。

显存不足 大模型小卡

--cpu-offload-params PARAMS list 默认: 空（非选择性卸载）

指定要卸载的参数名段。例如 --cpu-offload-params experts 仅卸载 MoE 专家权重， 保留注意力和 FFN 的非专家权重在 GPU 上。对 MoE 模型效果最好。

十二、Frontend — 前端服务配置

--host HOST / --port PORT str / int 默认: None / 8000

API 服务器监听地址。--host 0.0.0.0 允许外部访问，127.0.0.1 仅本地。

--api-key KEY [KEY ...] str 默认: None（不鉴权）

API 认证密钥。设置后客户端必须在 Header 中携带 Authorization: Bearer KEY。 支持多个密钥。

--chat-template TEMPLATE str 默认: 模型自带模板

自定义 chat 模板（Jinja2 格式）。可以是文件路径或内联模板字符串。 覆盖模型 tokenizer_config.json 中的默认模板。

--tool-call-parser {hermes,llama3_json,qwen3_coder,...} str 默认: None

工具调用解析器。不同模型使用不同的 function calling 格式：

模型推荐 parser

Function Calling Agent

--enable-auto-tool-choice flag

启用后，模型可以自动决定是否调用工具，而不需要客户端显式设置 tool_choice: "auto"。

--disable-frontend-multiprocessing flag 默认: False

禁用前端多进程。调试时有用，但生产环境应保持多进程以处理高并发 HTTP 请求。

--api-server-count COUNT, -asc int 默认: data_parallel_size

API 服务器进程数。多进程可提升 HTTP 请求处理能力和 tokenization 并行度。

十三、ObservabilityConfig — 可观测性配置

--disable-log-stats flag 默认: False

禁用统计日志输出（如每秒 token 数、KV cache 使用率等）。生产环境建议保留以监控性能。

--enable-log-requests flag 默认: False

记录每个请求的 ID、参数和 LoRA 信息。DEBUG 级别下还输出 prompt 内容。用于调试和审计。

--otlp-traces-endpoint URL str 默认: None

OpenTelemetry 追踪端点。将 trace 数据发送到 Jaeger、Zipkin 等后端，用于分布式链路追踪。

--enable-mfu-metrics flag

启用 MFU（Model FLOPs Utilization）指标，监控 GPU 算力利用率。

十四、场景化调优方案

场景 A：高并发在线 API 服务（纯文本）

# 目标: 最大化 QPS，可接受适度延迟
vllm serve /path/to/model \
  --max-model-len 8192            # 缩短序列上限，释放显存给并发
  --max-num-batched-tokens 32768    # 大 batch 饱和 GPU
  --max-num-seqs 512              # 高并发
  --gpu-memory-utilization 0.95    # 压榨显存
  --enable-prefix-caching          # 复用系统提示词 KV cache
  --enable-chunked-prefill         # 防止长 prefill 阻塞 decode
  --kv-cache-dtype fp8             # KV cache 减半，并发翻倍
  --performance-mode throughput    # 吞吐优先

场景 B：低延迟对话服务

# 目标: 最小化 TTFT 和每 token 延迟
vllm serve /path/to/model \
  --max-model-len 4096
  --max-num-batched-tokens 8192
  --max-num-seqs 64               # 少并发，每个请求分到更多资源
  --enable-chunked-prefill
  --performance-mode interactivity # 延迟优先
  --speculative-config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}' # 投机解码降低延迟

场景 C：视频/多模态推理

# 目标: 处理视频输入，优化 prefill 速度
vllm serve /path/to/model \
  --max-model-len 32768
  --max-num-batched-tokens 32768   # 大 batch 容纳视觉 token
  --max-num-seqs 32               # 视频请求占用大，少并发
  --gpu-memory-utilization 0.95
  --enable-chunked-prefill         # 必须开启：视觉 token 很长
  --media-io-kwargs '{"video":{"num_frames":64}}'  # 限制帧数！
  --limit-mm-per-prompt '{"video":1,"image":5}'
  # 不开 --speculative-config（prefill 为瓶颈，投机解码无用）
  # 不开 --enable-prefix-caching（视频输入无共享前缀）

场景 D：长上下文文档处理

# 目标: 支持 128K+ 上下文
vllm serve /path/to/model \
  --max-model-len 131072          # 128K 上下文
  --max-num-batched-tokens 16384
  --max-num-seqs 16               # 长上下文下并发自然低
  --gpu-memory-utilization 0.95
  --kv-cache-dtype fp8             # 关键！128K的KV cache非常大
  --enable-chunked-prefill

场景 E：多卡高吞吐（模型单卡可装）

# 4 张 H100/H200 跑 27B FP8：用 DP 而不是 TP
vllm serve /path/to/model \
  -tp 1 -dp 4                    # 4 路数据并行，吞吐 ≈ 4x
  --max-num-batched-tokens 32768
  --gpu-memory-utilization 0.95

场景 F：多 LoRA 多任务服务

vllm serve /path/to/base-model \
  --enable-lora
  --max-loras 4                    # 同时激活 4 个 LoRA
  --max-lora-rank 64
  --lora-modules chat=/lora/chat code=/lora/code math=/lora/math
调优决策树：
1. 模型装不下一张卡？ → 先试 FP8/AWQ 量化，仍不行再加 TP
2. 模型装得下，多卡？ → 用 DP 而不是 TP（吞吐线性增长，无通信开销）
3. 吞吐不够？ → 增大 max-num-batched-tokens + max-num-seqs
4. 延迟抖动大？ → 开启 chunked-prefill + async-scheduling
5. KV cache 不够？ → kv-cache-dtype=fp8，或缩小 max-model-len
6. 视频太慢？ → 减少 num_frames，关闭投机解码
