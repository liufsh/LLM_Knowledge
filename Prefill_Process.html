详细计算过程

概述：什么是 Prefill？

LLM 推理分为两个阶段：Prefill（预填充）和 Decode（解码）。 Prefill 是第一阶段——处理用户输入的 prompt，一次性并行计算所有 token， 生成初始的 KV Cache 和第一个输出 token。

Prefill 的三大目标： (1) 理解完整的 prompt 上下文； (2) 为每一层构建 KV Cache（供后续 Decode 复用）； (3) 预测 prompt 后面的第一个 token。

下面我们以 LLaMA-7B（32 层，32 头，d=4096）处理 "The cat sat on the mat" 为例，逐步追踪 Prefill 中的每一步计算。

图 1：Prefill 阶段完整计算流程总览。输入文本经过 Tokenization、Embedding、N 层 Transformer（含注意力和 FFN）、 最后经 LM Head 输出下一个 token 的概率分布。整个过程中同时构建 KV Cache。

Step 1：Tokenization（分词）

1.1 过程

Tokenizer 将原始字符串切分为子词 token 序列，每个 token 映射到词表中的整数 ID。 LLaMA 使用 SentencePiece BPE，词表大小 V = 32,000。

图 2：Tokenization 过程。原始字符串被 BPE 分词器切分为 6 个 token， 每个 token 映射到对应的词表 ID。注意 "▁" 前缀表示词前空格。

1.2 数值追踪

位置Token 文本Token ID说明
0"The"450句首单词，无空格前缀
1"▁cat"6635▁ 表示前面有空格

关键点：Tokenization 是纯字符串操作，不涉及任何神经网络计算。 在 CPU 上执行，耗时可忽略（微秒级）。输出形状：[6]（6 个整数 ID）。

Step 2：Embedding 查表

2.1 过程

Embedding 层是一个大型查找表 E ∈ R32000×4096。 给定 token ID，直接取出对应行——不做矩阵乘法，而是索引操作。

图 3：Embedding 查表过程。6 个 token ID 各从表中取出一行 4096 维向量， 组成输入矩阵 X ∈ R6×4096。注意：这是查表操作，零 FLOPs。

2.2 数值细节

X = E[token\_ids]   →   X ∈ R6 × 4096

Embedding 表参数量 = 32,000 × 4,096 = 131,072,000 (≈ 1.31 亿参数)
注意：此阶段不加位置编码。LLaMA 使用 RoPE， 位置信息在 Attention 层的 Q/K 投影之后才注入（通过旋转），而非在 Embedding 阶段加上去。 这与 GPT-2（Learned PE 加到 Embedding）和原始 Transformer（Sinusoidal PE 加到 Embedding）不同。

Step 3：Transformer 层前向传播（×32 层）

Embedding 输出 X 依次通过 32 层 Transformer Block。每层包含两个子模块： Self-Attention 和 SwiGLU FFN，各配 RMSNorm + 残差连接。 下面详细展开一层的计算。

3.1 子步骤 A：RMSNorm + Multi-Head Self-Attention

A1. RMSNorm（Pre-Normalization）

h_norm = h / RMS(h) × γ   其中 RMS(h) = √(mean(h2))

输入 [6, 4096] → 输出 [6, 4096]（形状不变，数值归一化）

A2. Q/K/V 线性投影

对归一化后的输入做三组独立的线性变换，生成 Query、Key、Value：

Q = h_norm · WQ   [6, 4096] × [4096, 4096] → [6, 4096]
K = h_norm · WK   [6, 4096] × [4096, 4096] → [6, 4096]
V = h_norm · WV   [6, 4096] × [4096, 4096] → [6, 4096]

然后 reshape 为 32 个头：Q, K, V → [6, 32, 128]

FLOPs：3 × 2 × 6 × 4096 × 4096 = 603M per layer

A3. 应用 RoPE 位置编码

对每个头的 Q 和 K 向量，根据其序列位置进行旋转。位置 0 的 Q/K 不旋转， 位置 1 旋转 θ 角，位置 5 旋转 5θ 角。旋转以 2D 对的方式独立进行， (q0, q1) 用频率 θ0 旋转，(q2, q3) 用 θ1 旋转... V 不做 RoPE。

A4. 注意力计算（Prefill 的核心！）

图 4：Prefill 阶段单个注意力头的完整计算流程。 Q ∈ [6,128]，K ∈ [6,128]，V ∈ [6,128]。 Q@KT 产生完整的 [6×6] 注意力矩阵，经因果掩码和 Softmax 后与 V 相乘。 右侧同时将 K、V 存入 KV Cache。

逐步计算（以单个头为例）：

  1. 注意力分数：S = Q · KT / √128 → [6, 6] 矩阵。 S[i][j] 表示位置 i 的 token 对位置 j 的"关注程度"。
  2. 因果掩码：将上三角（j > i 的位置）设为 -∞。 这保证每个 token 只能看到自己和之前的 token。
  3. Softmax：对每行做 softmax，将分数转为概率。每行之和 = 1。 被掩码的位置变为 0。
  4. 加权求和：Output = A · V → [6, 128]。 每个位置的输出是其能看到的所有 V 向量的加权平均。
Prefill 的 [6×6] vs Decode 的 [1×7]： Prefill 一次性计算完整的 N×N 注意力矩阵（这里是 6×6）， 36 个注意力对全部并行计算。而 Decode 每步只算 [1×t] 的单行向量。 这就是 Prefill 计算密集（充分利用 GPU 并行性） 而 Decode 内存密集的根本原因。

A5. 输出投影 + 残差

32 个头的输出 concat → [6, 4096]
× WO [4096, 4096] → [6, 4096]
+ 残差（加回原始输入 h）

A6. 存入 KV Cache

同时，将本层计算出的 K 和 V 存入 KV Cache。这是 Prefill 阶段的副产品 ——不需要额外计算，只是把已计算的结果保留下来：

KV Cache[layer_l] = { K: [6, 32, 128], V: [6, 32, 128] }

3.2 子步骤 B：RMSNorm + SwiGLU FFN

图 5：SwiGLU FFN 的计算流程。输入经两条并行路径（Gate + Up）， Gate 路径经过 SiLU 激活，两路逐元素相乘后经 Down 投影回原维度。

SwiGLU FFN 的三步计算：

  1. Gate 路径：gate = SiLU(h · Wgate)    [6, 4096] × [4096, 11008] → [6, 11008] → SiLU → [6, 11008]
  2. Up 路径：up = h · Wup    [6, 4096] × [4096, 11008] → [6, 11008]
  3. Down 投影：out = (gate ⊗ up) · Wdown    [6, 11008] × [11008, 4096] → [6, 4096] + 残差

FLOPs：3 × 2 × 6 × 4096 × 11008 = 1.62G per layer （FFN 的计算量约为 Attention 的 2.7 倍！）

Step 4：LM Head —— 输出层计算

经过 32 层 Transformer 后，得到最终隐藏状态 H ∈ R6×4096。 输出层将其转换为词表上的概率分布。

图 6：LM Head 输出计算。取最后一个位置（"mat"）的隐藏向量， 经 RMSNorm → 线性映射到 32000 维 → Softmax 得到概率分布。

4.1 为什么只取最后一个位置？

在自回归模型中，位置 i 的输出预测的是位置 i+1 的 token。 最后一个位置（位置 5，"mat"）的输出就是我们要的——它融合了整个 prompt 的上下文信息， 预测下一个 token。

训练 vs 推理的差异： 训练时，所有 6 个位置的 logits 都会被使用（分别与位置 1-6 的真实 token 计算损失）。 推理时，只需要最后一个位置的 logits 来生成下一个 token。

4.2 计算步骤

hlast = H[5]  →  [1, 4096]
hnorm = RMSNorm(hlast)  →  [1, 4096]
logits = hnorm · WvocabT  →  [1, 4096] × [4096, 32000] = [1, 32000]
probs = Softmax(logits)  →  [1, 32000]

next\_token = sample(probs)   或   argmax(probs)

Step 5：KV Cache 的构建

Prefill 阶段的另一个关键产出是 KV Cache——它是 Decode 阶段高效运行的基础。

图 7：Prefill 阶段构建的 KV Cache。每一层都存储了 6 个 token 的 K 和 V 向量（32 个头，每头 128 维）。 整个 Cache 在 Decode 阶段不再重新计算，只会被追加新 token 的 K/V。

为什么 Decode 慢？每生成一个 token，GPU 需要从显存加载完整的模型权重 （LLaMA-7B: ~14 GB）和全部 KV Cache，但只做极少量计算（一个 token 的矩阵向量乘）。 算力利用率不到 1%，大部分时间在等待数据搬运。 这就是为什么 Prefill 可能只需 200ms，但生成 100 个 token 却需要 2-3 秒。

Prefill 阶段的性能优化

1

FlashAttention

将 N×N 注意力矩阵分块计算，避免在 HBM 中物化完整矩阵。 内存从 O(N2) 降为 O(N)，速度提升 2-4 倍。这是 Prefill 的标准加速手段。

2

Chunked Prefill

将长 prompt 分成多个 chunk（如 512 tokens/chunk）依次处理， 避免一次性分配过大的注意力内存。每个 chunk 的 KV 追加到 Cache 中。 可与 Decode 请求交错调度（continuous batching）。

3

Tensor Parallelism

将 QKV 投影和 FFN 的权重矩阵切分到多 GPU，Prefill 的大矩阵乘法天然适合 TP—— 多卡并行计算加速线性，NVLink 通信开销可被计算完全覆盖。

4

Prefix Caching

如果多个请求共享相同的 system prompt 前缀，只需 Prefill 一次并缓存 KV Cache， 后续请求直接复用。减少 50-90% 的 Prefill 计算。代表：vLLM RadixAttention。

总结

Prefill 阶段是 LLM 推理的"启动引擎"，其核心工作可以用一句话概括：

将用户的文本 prompt 转化为两个关键产物： (1) KV Cache——所有 prompt token 在每层的 Key/Value 向量，供后续 Decode 复用； (2) 第一个输出 token——基于完整上下文预测的下一个最可能的词。

整个过程是完全并行的：所有 prompt token 同时通过所有 Transformer 层， 充分利用 GPU 的矩阵乘法并行性。这是 Prefill计算密集（而非内存密集）的根本原因， 也是它通常比逐 token 的 Decode 阶段快得多的原因。
