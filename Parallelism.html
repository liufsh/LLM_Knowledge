从数据并行到 3D 混合并行 —— 千卡训练和高效推理的工程基石
Data Parallel Tensor Parallel Pipeline Parallel ZeRO / FSDP Expert Parallel 集合通信

引言：为什么需要并行？

LLaMA-65B 有 652 亿参数，以 FP16 存储需要约 130 GB——单张 A100 (80GB) 连模型都放不下， 更别说训练时还需要梯度、优化器状态和激活值。训练 1.4T token 需要 ~5.5×1023 FLOPs， 即使单卡 A100 的 312 TFLOPS 峰值跑满，也需要 20,000+ 天。

并行的两大目标： (1) 容量——将放不下的模型分散到多张 GPU 上； (2) 速度——将无法接受的训练时间缩短到可行范围（如 21 天 × 2048 张 A100）。

本文将系统介绍大模型训练和推理中的六种核心并行策略、底层的集合通信原语、以及工程实践中的组合方式。

一、数据并行（Data Parallelism, DP）

1.1 核心思想

数据并行是最简单、最基础的并行方式：每张 GPU 持有完整的模型副本， 训练数据被均匀切分给各 GPU。每张 GPU 独立做前向和反向传播，然后同步梯度。

图 1：数据并行的工作流程。训练 batch 被分成 N 份，每张 GPU 用自己的子集独立计算梯度， 通过 AllReduce 取平均后各自更新参数。

1.2 训练步骤

  1. 数据切分：一个 global batch（如 32 样本）被分成 N 份 micro-batch（每 GPU 8 样本）
  2. 独立计算：每张 GPU 用自己的 micro-batch 做前向 + 反向传播，计算局部梯度
  3. 梯度同步：通过 AllReduce 操作对所有 GPU 的梯度取平均
  4. 参数更新：每张 GPU 用相同的平均梯度更新自己的模型副本
通信量 = 2 × |params| × (N-1)/N    (Ring AllReduce)

✓ 优点

  • 实现简单（PyTorch DDP 几行代码）
  • 近线性扩展（通信可与计算重叠）
  • GPU 间通信量与 GPU 数无关

✗ 缺点

  • 每张 GPU 存全部参数——模型太大时放不下
  • 优化器状态（Adam 2 份动量）也要每卡存一份
  • 内存效率低：N 张卡存了 N 份相同的参数

二、张量并行（Tensor Parallelism, TP）

2.1 核心思想

张量并行把单个层的权重矩阵切分到多张 GPU。每张 GPU 只持有权重的一部分， 计算也只做对应的部分，然后通过通信拼合结果。

图 2：张量并行将权重矩阵按列（或按行）切分到 4 张 GPU 上。 每 GPU 计算部分结果，通过 AllGather 拼合为完整输出。

2.2 Megatron-LM 风格的切分

Megatron-LM（Shoeybi et al., 2019）提出了经典的 TP 方案，针对 Transformer 的两个子层：

1

MLP 层切分

第一个线性层 W1 按列切分（Column Parallel）， 每 GPU 计算输出的一部分维度。第二个线性层 W2 按行切分（Row Parallel）， 各 GPU 的部分结果直接相加得到最终输出。
通信：前向 1 次 AllReduce，反向 1 次 AllReduce。

2

Attention 层切分

Q/K/V 投影矩阵按注意力头切分——每 GPU 负责 h/N 个头的完整计算。 输出投影 WO 按行切分。
通信：前向 1 次 AllReduce，反向 1 次 AllReduce。

通信频率高：TP 在每一层都需要通信（AllReduce 或 AllGather）， 而 Transformer 可能有 80 层。因此 TP 强烈依赖高带宽互连—— 通常要求 GPU 在同一节点内，通过 NVLink（600-900 GB/s）连接。 跨节点的 InfiniBand（200-400 GB/s）带宽不够用。

2.3 序列并行（Sequence Parallelism, SP）

Megatron-LM v2 引入了序列并行：在非张量并行的操作（如 LayerNorm、Dropout）上， 沿序列长度维度切分。这减少了激活值的冗余存储—— TP 中每张 GPU 的 LayerNorm 输入/输出本来是完整的 [seq, d]， SP 将其切为 [seq/N, d]，内存进一步降低。

✓ 优点

  • 单层的内存和计算都被 N 等分
  • 降低单个 token 的推理延迟（多卡并行算一个请求）
  • 与 DP、PP 正交，可自由组合

✗ 缺点

  • 每层两次 AllReduce，通信极频繁
  • 必须在高带宽互连（NVLink）上使用
  • 实现复杂，需要精心设计矩阵切分

三、流水线并行（Pipeline Parallelism, PP）

3.1 核心思想

流水线并行把模型按层分组，不同组放在不同 GPU 上。 数据像流水线一样依次通过各级 GPU。

图 3：流水线并行将 32 层模型分成 4 级（每级 8 层），分配到 4 张 GPU。 训练 batch 被切为多个 micro-batch，像流水线一样依次通过各级。灰色区域是"流水线气泡"（GPU 空闲）。

3.2 流水线气泡（Pipeline Bubble）

PP 的核心问题是气泡——在流水线启动和排空阶段，部分 GPU 处于空闲状态。

气泡比例 ≈ (P - 1) / (M + P - 1)    P=流水线级数, M=micro-batch 数

例如 P=4, M=4 时气泡比例 = 3/7 ≈ 43%，近一半时间被浪费！ 解决方案是增大 M（更多 micro-batch），使 M >> P，气泡比例趋近于 0。

3.3 调度策略

策略气泡率内存特点
GPipe(P-1)/M高（存所有 micro-batch 的激活）简单，同步调度
1F1B(P-1)/M低（只存 P 个 micro-batch 的激活）交错前向和反向
Interleaved 1F1B(P-1)/(M×v)中每 GPU 持有多个不连续的层组，v 为虚拟级数
Zero Bubble PP≈0高将反向传播拆为 B 和 W 两步，用 W 步填充气泡
PP 的通信优势：PP 只在相邻级之间做点对点（P2P）通信， 传输的是激活值张量（远小于完整参数）。通信量小、频率低， 适合跨节点（InfiniBand）使用——这是 PP 与 TP 的关键区别。

四、集合通信原语（Collective Operations）

所有并行策略的底层都依赖于一组集合通信操作。理解这些原语是理解并行策略的基础。

图 4：六种基础集合通信操作的直观图解。每行表示一张 GPU，左列为操作前的数据分布，右列为操作后。
操作功能通信量（每 GPU）使用场景

关键关系：AllReduce = ReduceScatter + AllGather。 理解这个分解很重要——FSDP/ZeRO 正是利用这个拆分，将 AllReduce 拆成两步， 使得中间结果可以保持分片存储，从而减少内存占用。

4.2 Ring AllReduce

最常用的 AllReduce 实现是 Ring AllReduce：N 张 GPU 排成一个环， 数据被分成 N 块，经过 2×(N-1) 步传输完成。每步只传 |data|/N 的数据量， 总通信量为 2×|data|×(N-1)/N——与 GPU 数量 N 无关。

4.3 All-to-All 通信原语

All-to-All（也称 Personalized All-to-All 或 Transpose 操作）是所有集合通信中 最"个性化"的一个：每个 GPU 向其他每个 GPU 发送不同的数据块。 与 AllReduce（所有 GPU 发送相同数据）和 AllGather（每 GPU 发送一块、所有 GPU 收完整）不同， All-to-All 的每一对 GPU 之间传输的数据内容都是独立的。

All-to-All: GPUi 的第 j 块数据 → GPUj 的第 i 块

等价于对 [N × N] 的数据块矩阵做转置
图 5：All-to-All 通信原语。左图：基本数据移动——GPUi 的第 j 块（颜色 = 目标 GPU） 发送到 GPUj。右图：MoE 中的实际应用——Router 为每个 token 指定目标专家， All-to-All 将 token 路由到对应 GPU。

All-to-All 的具体语义

假设有 4 个 GPU，每个 GPU 持有一个数据张量，被均分为 4 个块：

块 0（给 GPU0）块 1（给 GPU1）块 2（给 GPU2）块 3（给 GPU3）
GPU 0 持有A0A1A2A3
GPU 1 持有B0B1B2B3
GPU 2 持有C0C1C2C3
GPU 3 持有D0D1D2D3

All-to-All 之后：

来自 GPU0来自 GPU1来自 GPU2来自 GPU3
GPU 0 收到A0B0C0D0
GPU 1 收到A1B1C1D1
GPU 2 收到A2B2C2D2
GPU 3 收到A3B3C3D3
直觉理解：如果把 N 个 GPU 的数据排成一个 [N × N] 的块矩阵， All-to-All 就是对这个矩阵做转置——第 i 行第 j 列的块 移到第 j 行第 i 列。这就是为什么 All-to-All 也被称为 "Distributed Transpose"。

通信量分析

每个 GPU 发送 (N-1) 个块（自己留一块不需要发），每个块大小 = |data|/N
总通信量/GPU = |data| × (N-1)/N
系统总通信量 = N × |data| × (N-1)/N = |data| × (N-1)

All-to-All 在 MoE 中的两次调用

在 MoE（Mixture of Experts）层中，All-to-All 被调用两次：

  1. Dispatch（分发）：Router 为每个 token 选择 Top-k 个专家后， All-to-All 将 token 的隐藏状态发送到目标专家所在的 GPU。每个 GPU 从所有其他 GPU 收集路由到本地专家的 token。
  2. Combine（收回）：专家计算完成后，All-to-All 将处理结果 发送回原始 GPU（按 token 的源 GPU 路由）。 这次传输的数据与第一次方向相反。
All-to-All 的工程挑战：
  • 通信模式不规则：不同 GPU 对之间的数据量可能不同（取决于 Router 的路由决策）， 导致难以利用 Ring 等规则拓扑优化。
  • 负载不均衡：如果大量 token 被路由到同一个专家（"热门专家"问题）， 对应 GPU 收到的数据远多于其他 GPU，成为瓶颈。
  • 带宽需求高：All-to-All 需要全连接带宽（每对 GPU 之间都有数据传输）， 比 Ring 拓扑需要的带宽更高。通常要求高速互连（NVLink 或高带宽 InfiniBand）。

五、ZeRO 与 FSDP —— 内存高效的数据并行

5.1 问题：DP 的内存冗余

标准 DP 中，每张 GPU 存储完整的：参数 + 梯度 + 优化器状态。 对于一个 7B 参数的模型（FP16），每张 GPU 的内存占用为：

  • 参数：7B × 2 bytes = 14 GB
  • 梯度：14 GB
  • Adam 优化器状态（FP32 参数副本 + 一阶动量 + 二阶动量）：7B × 12 bytes = 84 GB
  • 总计：112 GB / 卡——比 A100 的 80 GB 还大！

5.2 ZeRO 三阶段

ZeRO（Zero Redundancy Optimizer, Rajbhandari et al., 2020）的核心思想： 不同 GPU 各存 1/N 份，需要时再通信聚合。分三个渐进阶段：

5.3 FSDP（Fully Sharded Data Parallel）

FSDP 是 PyTorch 对 ZeRO-3 的原生实现。其训练步骤：

图 8：FSDP 的单步训练流程。参数平时以分片形式存储（每 GPU 只存 1/N）， 计算某层时通过 AllGather 临时聚合完整参数，计算完成后立即释放，反向传播后通过 ReduceScatter 分发梯度。
通信开销：FSDP 在每一层的前向和反向传播中都要做一次 AllGather（聚合参数） 和一次 ReduceScatter（分发梯度），通信总量约为标准 DP 的 1.5 倍。 但由于通信可以与计算流水线重叠（prefetch 下一层参数）， 实际训练速度损失通常仅 5-15%。

六、3D 混合并行 —— 实际训练的标准方案

6.1 为什么需要混合？

单一并行策略都有局限：DP 无法处理超大模型，TP 受限于节点内带宽，PP 有气泡开销。 实际训练将三者组合，各取所长：

  • TP：在节点内使用（NVLink 高带宽），通常 TP=4 或 8
  • PP：在节点间使用（InfiniBand），通常 PP=2-8
  • DP/FSDP：在最外层使用，扩展到更多节点
图 9：3D 并行的组织结构。16 张 GPU 被组织为 DP=2 × TP=4 × PP=2。 TP 组在节点内（NVLink），PP 和 DP 跨节点（InfiniBand）。

6.2 实际配置示例

模型总 GPUDPTPPP总计
LLaMA-7B12812811纯 DP（模型够小）
LLaMA-13B2566422DP=64, TP=2, PP=2
LLaMA-65B20486484DP=64, TP=8, PP=4

配置原则： (1) TP 度 ≤ 节点内 GPU 数（受 NVLink 约束）； (2) PP 度适中（太大则气泡太多）； (3) DP 度 = 总 GPU / (TP × PP)，越大越好（通信可重叠）； (4) 总 batch size = DP × micro_batch × gradient_accumulation_steps。

七、专家并行（Expert Parallelism）

7.1 MoE 模型的并行需求

Mixture-of-Experts（MoE）模型（如 Mixtral 8x7B、DeepSeek-V3）将 FFN 层替换为多个"专家"， 每个 token 只激活其中 k 个。专家并行将不同专家放在不同 GPU 上：

图 10：专家并行的工作流程。Router 网络决定每个 token 交给哪两个专家处理（Top-2）， 通过 All-to-All 通信将 token 路由到对应 GPU 上的专家，计算后再通过 All-to-All 收回结果。

7.2 All-to-All 通信

专家并行的核心通信原语是 All-to-All：每张 GPU 向其他所有 GPU 发送不同的数据。 这与 AllReduce（所有 GPU 发送相同数据）不同——All-to-All 的通信模式更不规则， 对网络拓扑的要求更高。

负载均衡挑战：如果 Router 将大部分 token 路由到少数几个专家， 对应 GPU 成为瓶颈。实践中通过 辅助损失（auxiliary load balancing loss） 鼓励均匀路由，以及 容量因子（capacity factor）限制每个专家处理的 token 数。

八、上下文并行（Context Parallelism, CP）

8.1 动机：长序列的内存瓶颈

当上下文窗口从 4K 扩展到 128K 甚至 1M 时，注意力计算的 O(N2) 内存需求成为训练的主要瓶颈——即使用了 FlashAttention 将峰值内存降为 O(N)， KV Cache 和激活值仍然随序列长度线性增长。128K 序列的激活值可能占满整张 A100 的显存， 即使模型参数本身并不大。

核心问题：TP 切分模型宽度（权重矩阵），PP 切分模型深度（层）， DP 切分数据 batch——但没有一个切分序列长度。 当单条序列太长时，这三种并行都无济于事。CP 正是填补这一空白的方案。

8.2 核心思想

上下文并行将单条序列沿序列长度维度切分到多张 GPU 上。 每张 GPU 只持有序列的一个片段（chunk），计算该片段的注意力时， 通过通信获取其他片段的 KV 信息。

图 11：上下文并行将 128K 序列切为 4 段，分配到 4 张 GPU。 每张 GPU 只存储自己片段的 Q、K、V 和激活值。通过 Ring Attention 机制， KV 块在 GPU 之间沿环形拓扑传递，每个 GPU 逐步积累完整的注意力结果。

8.3 Ring Attention：CP 的通信机制

Ring Attention（Liu et al., 2023）是实现 CP 的核心算法。其工作方式：

  1. 初始化：将序列均分为 CP 份，GPUi 持有第 i 个片段的 Qi、Ki、Vi
  2. 本地计算：每张 GPU 先计算 Qi 与本地 Ki、Vi 的注意力（本地块）
  3. Ring 传递：每张 GPU 将自己的 KV 块发送给环中的下一张 GPU，同时从上一张接收 KV 块
  4. 远程计算：用接收到的远程 KV 块更新注意力结果（使用 Online Softmax 在线累积）
  5. 重复步骤 3-4 共 CP-1 轮，直到每张 GPU 都与所有 KV 块完成了注意力计算
每轮：GPUi 发送 KVi → GPU(i+1) mod CP
经过 CP-1 轮后，每张 GPU 已看到全部 CP 个 KV 块
计算-通信重叠：Ring Attention 的关键优势在于，KV 传输和注意力计算可以完美重叠—— GPU 在计算当前接收到的 KV 块的注意力时，同时将上一个 KV 块发送给下一张 GPU。 只要每块的计算时间 ≥ 传输时间，通信开销就可以被完全隐藏。

8.5 CP 的变体与优化

1

Ring Attention

基础版本。KV 块沿环形拓扑逐步传递，与 FlashAttention 的分块计算天然兼容。 适用于因果注意力和双向注意力。

2

Striped Attention

不按连续段切分序列，而是交错分配 token（如 GPU0 取偶数位，GPU1 取奇数位）。 更均匀的负载分布，避免因果掩码导致的计算不均衡（前面的 chunk 工作量远少于后面的）。

3

USP (Unified Sequence Parallel)

DeepSpeed-Ulysses 方案。将 Q 沿序列维切分，K/V 通过 AllGather 聚合完整版本， 然后每 GPU 对自己的 Q 块做完整 Attention。通信模式更简单，但 KV 聚合占用更多内存。

4

Hybrid CP + TP

在节点内使用 TP（切权重），跨节点使用 CP（切序列），实现 4D 并行。 LLaMA-3.1 的 128K 训练采用此方案：TP=8（节点内）+ CP=4-8（跨节点）。

8.6 因果掩码下的负载均衡

因果注意力中，序列前部的 token 只关注少数前文，后部的 token 需要关注全部前文。 如果按连续段切分，最后一个 chunk 的计算量远大于第一个，导致负载不均衡。

解决方案： (1) Zigzag 分配：将 token 按锯齿形分配（0,7,8,15 给 GPU0；1,6,9,14 给 GPU1...）， 使每 GPU 的计算量近似相等； (2) Striped 分配：交错分配 token； (3) 过采样 + 丢弃：每 GPU 计算稍多的注意力对，丢弃掉被掩码的部分。

8.7 CP 与其他序列维并行的对比

方案切分维度通信模式内存节省适用互连代表实现
Sequence Parallel (SP) 非 Attention 操作的序列维（LayerNorm, Dropout） AllGather / ReduceScatter 仅激活值（小） NVLink Megatron-LM v2
Context Parallel (CP) Attention 的序列维（Q/K/V 全切分） Ring P2P / AllGather 激活值 + KV Cache（大） NVLink / IB Ring Attention, Megatron-CP
Ulysses SP Q 沿序列维，K/V AllGather AllGather + ReduceScatter 激活值（中） NVLink DeepSpeed-Ulysses

✓ CP 优点

  • 线性降低每 GPU 的激活值和 KV Cache 内存
  • 通信可与计算完美重叠（Ring Attention）
  • 与 TP/PP/DP 正交，可自由组合为 4D/5D 并行
  • 使 128K-1M+ 上下文训练成为可能
  • 不改变模型数学——输出与无 CP 时完全一致

✗ CP 缺点

  • 通信轮次 = CP-1，CP 越大通信越多
  • 因果掩码下负载不均衡需额外处理
  • 实现复杂度高（在线 Softmax + 通信调度）
  • 主要帮助长序列场景，短序列收益有限
实际案例：LLaMA-3.1 将上下文从 8K 扩展到 128K，训练配置为 DP × TP=8 × PP=4 × CP=8 = 16,384 张 H100 GPU。 其中 CP=8 将 128K 序列切为 8 段，每 GPU 只处理 16K token 的注意力计算， 激活值内存降为原来的 1/8。没有 CP，128K 训练在当前硬件上基本不可行。

九、推理并行策略

推理和训练的并行需求不同——推理没有反向传播，优化目标是低延迟或高吞吐。

图 13：推理的两种并行策略。TP（左）将单个请求切分到多 GPU，降低延迟； DP（右）不同 GPU 处理不同请求，提升吞吐。
1

TP 推理（低延迟）

将模型切分到多 GPU，单个请求并行计算。首 token 延迟（TTFT）和每 token 延迟都降低。 适合交互式场景（聊天、实时对话）。代价是需要 NVLink 互连。

2

DP 推理（高吞吐）

每 GPU 加载完整模型，不同请求发往不同 GPU。无 GPU 间通信。 适合批量处理场景（离线翻译、批量总结）。要求每卡能放下完整模型。

3

PP 推理（流水线）

适用于模型太大无法单卡放下，但不需要极低延迟的场景。 多个请求可以像流水线一样在不同层级间流动。延迟较高但吞吐可接受。

4

Prefill-Decode 分离

Prefill 阶段（计算密集）和 Decode 阶段（内存密集）分配到不同的 GPU 集群。 各自针对性优化硬件配置。代表：Splitwise, DistServe。

实践决策树

1. 模型能放进单卡吗？
  能 → 纯 DP（最简单、效率最高）

2. 模型放不下单卡但能放进单节点（8 GPU）吗？
  能 → TP=8（节点内 NVLink）+ DP 跨节点
  或 → FSDP（无需手动切分模型）

3. 模型连单节点都放不下？
  → 3D 并行：节点内 TP，节点间 PP + FSDP

4. 序列超长（128K+）？
  → 在上述基础上加 CP（上下文并行），将序列切分到多 GPU

5. MoE 模型？
  → 在上述基础上加 EP 切分专家

十一、总结

大模型的并行训练是一个系统工程，需要在计算、内存和通信之间精心平衡：

  1. 数据并行是基础——简单、高效，但无法解决模型太大的问题。
  2. ZeRO/FSDP 通过参数分片消除冗余，以少量通信换取 N 倍内存节省。
  3. 张量并行将矩阵运算切到节点内多 GPU，降低单层延迟，但要求高带宽互连。
  4. 流水线并行将模型按层切到跨节点 GPU，通信量小但有气泡开销。
  5. 上下文并行将序列沿长度维切分，通过 Ring Attention 使 128K+ 训练成为可能。
  6. 专家并行是 MoE 模型的专用方案，通过 All-to-All 通信路由 token。
  7. 多维混合并行组合上述策略（如 LLaMA-3.1 的 DP×TP×PP×CP），是千卡训练的标准方案。
一句话总结： TP 在节点内切矩阵，PP 在节点间切层，CP 沿序列切上下文， DP/FSDP 在最外层切数据——多维正交组合，配合 AllReduce、AllGather、Ring P2P 等集合通信原语， 使得数万张 GPU 能协同训练出百亿甚至万亿参数的模型，支持 128K+ 的超长上下文。
