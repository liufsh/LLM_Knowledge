一、背景：LLM 推理的瓶颈

LLM 推理的核心挑战在于其自回归特性——模型必须逐 token 生成， 每生成一个 token 都需要一次完整的前向传播。而不同请求的 prompt 长度和生成长度差异巨大 （可能相差 10-100 倍），这使得传统批处理方式效率极低。

vLLM 的核心贡献： (1) PagedAttention——用虚拟内存管理思想管理 KV Cache，消除 60-80% 的内存浪费； (2) Continuous Batching——每个迭代步都可以动态加入/移除请求， GPU 利用率从 ~30% 提升到 ~90%。两者结合使吞吐量提升 2-4 倍。

二、Static Batching vs Continuous Batching

2.1 Static Batching 的问题

传统做法是将多个请求打包成一个 batch一次性处理。 但因为不同请求的生成长度不同，整个 batch 必须等待最慢的请求完成才能释放：

  • 请求 A 生成了 200 个 token（10 秒）
  • 请求 B 生成了 50 个 token（2.5 秒）——但它必须等 A 完成才能返回
  • 请求 C 生成了 30 个 token（1.5 秒）——同样在等待
  • B 和 C 在后 7.5 秒里完全空转，GPU 资源被浪费

2.2 Continuous Batching：迭代级调度

Continuous Batching 的核心思想极其简洁：不在 batch 级别管理请求， 而在每个迭代步（iteration）级别管理。每次前向传播之前，调度器重新决定：

  1. 哪些正在进行的请求继续生成（decode）？
  2. 哪些已完成的请求需要移除？
  3. 哪些新到达的请求可以加入？
图 1：Static Batching（上）vs Continuous Batching（下）。 上图中 B 和 C 完成后必须空转等待 A；下图中 B 完成后立刻被 D 替换，C 完成后被 E 替换——无空闲 GPU 周期。
效果：Continuous Batching 将 GPU 的有效利用率从 Static Batching 的 ~30-50% 提升到 ~80-95%，吞吐量提升 2-4 倍。首次提出于 Orca（Yu et al., 2022）， 被 vLLM 进一步完善并与 PagedAttention 结合。

3.2 逐步骤详细追踪

以下以一个具体场景展示 6 个迭代步的完整过程：

图 2：Continuous Batching 的迭代级调度过程。每个迭代步，调度器动态调整 batch 组成—— Req B 在 Iter 4 完成后立即被 Req D 的 prefill 替换；Req C 完成后被 Req E 替换。

Iteration 1：初始 Prefill

  • 等待队列：{A(prompt=5 tokens), B(prompt=3 tokens), C(prompt=7 tokens)}
  • 调度器判断 GPU 内存足够，将三者全部加入 batch
  • Prefill 执行：A 处理 5 个 token，B 处理 3 个 token，C 处理 7 个 token
  • 每个请求的 KV Cache 被构建：分配页面（PagedAttention）
  • 每个请求生成第一个输出 token

Iteration 2-3：并行 Decode

  • Batch = {A(decode), B(decode), C(decode)}，共 3 个请求，每请求 1 个 token
  • GPU 执行：3 个 token 的 QKV 投影 + 注意力 + FFN，打包为一个小 batch
  • 每个请求各自追加 1 个 token 到 KV Cache
  • 采样得到 3 个新 token，拼接到各自的生成序列

Iteration 4：B 完成

  • B 生成了 EOS token 或达到 max_len → 标记为完成
  • B 的结果返回给客户端，立即释放 B 的全部 KV Cache 页面
  • Batch 变为 {A(decode), C(decode)}，只有 2 个请求
  • 关键区别：Static Batching 中 B 的 slot 会空转到 A 和 C 都完成； Continuous Batching 中这个 slot 立刻空出来给新请求

Iteration 5：D 加入（Prefill + Decode 混合）

  • 等待队列中有新请求 D(prompt=4 tokens)
  • 调度器将 D 加入 batch：Batch = {A(decode, 1 tok), C(decode, 1 tok), D(prefill, 4 toks)}
  • 混合 batch：A 和 C 各做 1 个 token 的 decode，D 做 4 个 token 的 prefill
  • GPU 在一次前向传播中同时处理 decode 和 prefill 请求

Iteration 6：C 完成，E 加入

  • C 完成 → 释放 KV Cache → E 加入
  • Batch = {A(decode), D(decode), E(prefill)}
  • 循环持续……直到所有请求处理完毕

3.3 混合 Prefill + Decode 的计算细节

图 3：单个迭代中 Prefill 和 Decode 混合执行的细节。Decode 请求各有 1 个新 token， Prefill 请求有 128 个 token，在注意力层分别计算（序列长度不同），在 FFN 层可合并为 130 token 的大 batch。

混合 batch 中的计算分两部分：

  1. 注意力层：每个请求独立计算（因为 KV Cache 长度不同）。 Decode 请求计算 [1 × ti] 的注意力向量，Prefill 请求计算 [n × n] 的注意力矩阵。 在 FlashAttention 实现中通过变长注意力（variable-length attention）支持。
  2. FFN 层：所有请求的 token 合并为一个大 batch。 如果有 2 个 decode（各 1 token）+ 1 个 prefill（128 tokens）， FFN 收到的是 [130, d] 的矩阵——充分利用 GPU 的并行性。
为什么混合有效？Decode 请求只有 1 个 token，FFN 层的矩阵乘法几乎不饱和 GPU； 将 Prefill 的多个 token 混入同一 batch，填满了 GPU 的计算间隙。 这就像高速公路上，小车（decode）和大车（prefill）可以并行使用不同车道，而非排队等候。

四、PagedAttention：虚拟内存管理 KV Cache

4.1 问题：KV Cache 的内存碎片

传统推理系统为每个请求预分配最大长度（如 2048 token）的连续 KV Cache 内存。 但实际生成长度往往远小于最大值——导致大量显存被预留但未使用。 此外，连续分配还导致外部碎片——即使总剩余显存足够，也可能因碎片无法分配新请求。

4.2 PagedAttention 的解决方案

vLLM 借鉴操作系统的虚拟内存 + 分页机制：

  • 将 KV Cache 分成固定大小的页（page/block），每页存储 k 个 token 的 KV（通常 k=16）
  • 不要求页在物理显存中连续——可以散布在任意位置
  • 通过Block Table（页表）维护逻辑页号到物理页号的映射
  • 新 token 生成时，只在需要时按需分配新页，而非预分配最大长度
图 4：传统连续分配（左）vs PagedAttention 分页分配（右）。 左图中每个请求预分配 max_len 的连续空间，实际使用仅 25%，浪费 ~75%； 右图中页按需分配、可不连续，浪费 <4%（仅最后一页可能有内部碎片）。

4.3 Block Table（页表）

每个请求维护一个 Block Table，记录其逻辑页号到物理页号的映射：

请求逻辑页 0逻辑页 1逻辑页 2逻辑页 3已用 token
Req A物理页 7物理页 2物理页 15物理页 958
Req B物理页 3物理页 11--28
Req C物理页 0物理页 5物理页 13-42

注意力计算时，通过 Block Table 索引物理页，从不连续的显存位置收集 KV 数据。 vLLM 的自定义 CUDA kernel 实现了这种"收集式"注意力计算。

4.4 Copy-on-Write（写时复制）

当多个请求共享相同的 prompt 前缀（如 system prompt）时，PagedAttention 可以让它们 共享同一组物理页——只有当某个请求修改了共享页的内容时，才复制一份新的。 这大幅节省了具有相同 system prompt 的多请求场景的显存。

特殊路径：

  • Preemption（抢占）：当显存不足时，低优先级请求的 KV Cache 可以被swap 到 CPU 内存， 为高优先级请求腾出空间。被抢占的请求回到 Waiting 状态，后续可以恢复（从 CPU swap 回 GPU 或重新 prefill）。
  • Recompute vs Swap：被抢占时有两种恢复策略——重新计算 KV Cache（prefill 开销） 或从 CPU 内存 swap 回来（I/O 开销）。vLLM 根据 prompt 长度和 PCIe 带宽自动选择。

5.3 Budget 控制

每个迭代步，Scheduler 根据以下预算约束决定 batch 大小：

  • GPU 显存预算：当前可用的 KV Cache 页数 ≥ 新请求所需的页数
  • 最大 batch tokens：单步处理的总 token 数上限（prefill + decode tokens 之和）
  • 最大 batch 请求数：同时在 batch 中的请求数上限
Prefill 与 Decode 的平衡：一个长 prefill（如 4096 tokens）和一个 decode（1 token） 的计算量差异巨大。vLLM 通过 Chunked Prefill 将长 prefill 拆成多个 chunk （如 512 tokens/chunk），分多步执行，避免单个 prefill 独占 GPU 太久影响 decode 的延迟。

API Server

提供 OpenAI 兼容 API（/v1/chat/completions）。接收 HTTP 请求，放入请求队列， 流式返回生成结果（SSE/WebSocket）。

2

Scheduler

核心调度引擎。每个迭代步决定 batch 组成——哪些请求 prefill、哪些 decode、 哪些新加入、哪些被抢占。实现 Continuous Batching 的核心逻辑。

3

管理 KV Cache 的分页分配。维护空闲页池、每请求的 Block Table、引用计数（用于 CoW）。 分配/释放页面的决策反馈给 Scheduler。

4

Model Executor

执行模型前向传播。支持 TP（节点内多 GPU）和 PP（多节点）。 使用自定义 CUDA kernel 实现 PagedAttention，集成 FlashAttention。

八、vLLM 高级特性

1

Prefix Caching

多个请求共享相同 system prompt 时，自动复用 KV Cache。 通过哈希匹配 prompt 前缀，命中则跳过 prefill，直接复用缓存的 KV 页。

2

Speculative Decoding

用小模型（draft model）并行猜测多个 token，大模型一次性验证。 命中率高时可加速 2-3 倍。vLLM 内建支持。

3

Chunked Prefill

将长 prompt 拆为多个 chunk 分步 prefill，与 decode 请求交错执行。 避免长 prefill 独占 GPU 导致其他请求的 decode 延迟飙升。

4

Tensor Parallelism

支持单节点多 GPU 的 TP 推理。权重自动切分，KV Cache 页分布在各 GPU 上。 配合 NCCL 实现高效的跨 GPU 通信。

5

Quantization

支持 AWQ、GPTQ、SqueezeLLM 等量化方案，以及 FP8 KV Cache。 减少显存占用，支持更大 batch 或更大模型。

6

Multi-LoRA

同时加载多个 LoRA adapter，不同请求可以使用不同的 LoRA。 基座模型共享，LoRA 权重按需激活。

十、总结

vLLM 的核心技术栈可以归纳为三层：

  1. 调度层（Continuous Batching）：在每个迭代步动态组织 batch—— 完成的请求立即释放，新请求立即加入，prefill 和 decode 可以混合执行。 这消除了 Static Batching 中"等最慢请求"的浪费。
  2. 内存管理层（PagedAttention）：将 KV Cache 分成固定大小的页， 按需分配、不需连续，通过页表管理逻辑到物理的映射。 这消除了预分配的显存浪费和碎片问题。
  3. 执行层（Optimized Kernels）：自定义 CUDA kernel 实现分页注意力计算， 集成 FlashAttention、FP8 量化等底层优化。
一句话理解 Continuous Batching： 不再把"一批请求"当作一个不可分割的单位来处理， 而是把每个迭代步当作调度的最小粒度—— 每一步都重新审视"谁该继续、谁该离开、谁该加入"， 让 GPU 的每一个计算周期都用在有效的 token 生成上。 配合 PagedAttention 的按需分页，实现了接近零浪费的 LLM 推理。
